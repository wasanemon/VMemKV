## 1. 背景と問い

FaultKV は OS の仮想メモリ機構（mmap, swap, ページキャッシュ）を KVS のバッファ管理に使う設計です。カーネルがページの eviction・fetch・aging を担い、アプリケーション側では明示的なバッファ管理を行いません。

この設計に対する自然な問いがあります：

> **「OS に委任したページ管理は、ユーザランドで自前実装したページ管理（LRU など）に比べて、どの程度競争力があるのか？」**

直感的には、OS の page cache は「誰でも使えて賢い」一方、アプリケーション LRU は「自分のデータだけを管理する専用バッファ」です。
しかし，基本的に，データベースの設計において前者は非推奨でした．[Andy Pavlo のMMAPに関する論文](https://db.cs.cmu.edu/papers/2022/cidr2022-p13-crotty.pdf) ではMMAPによるデータベース実装は強く非推奨とされています．
とはいえ，FaultKVではこのAndy Pavlo論文で指摘されている問題の多くは回避する設計をとっています（[高レベル設計](../docs/specification/high%20level%20design.md), [低レベル設計](../docs/specification/low%20level%20design.md) 参照）．純粋に読み込みだけを問題にしたとき，どちらが優れているかは自明ではなく、実測で検証する必要があります。そこで 2 種類の環境（macOS / Linux）でマイクロベンチマークを実施しました。

### 短い答え

> **ストレージが遅い環境（クラウド VM・HDD など）であれば、mmap はバッファ管理コードを一行も書かずに pread+LRU と同等以上の性能を出す。**

実測の核心は次の 1 点です。ストレージの I/O レイテンシが大きい場合（本実験の Linux KVM: ~150 µs）、mmap の page fault コスト（~166 µs）と pread の miss コスト（~150 µs）はほぼ等しくなります。ミスコストが揃ってしまえば、あとは hit 時の速さ（mmap: ~0.2 µs 対 LRU: ~1 µs）だけが差を生みます。Zipf α=1.0 という標準的な局所性でも LRU hit 率は約 50% あるため、この hit コスト差が 1M 回積み重なり mmap が 1.4× 上回ります。

| 環境         | ストレージ         | cold (α=1.0)       | cold (α=0.5)      | cold (α=2.0)       |
| ------------ | ------------------ | ------------------ | ----------------- | ------------------ |
| macOS M4 Pro | ~1 µs pread miss   | LRU **49×** 速い   | LRU **83×** 速い  | LRU **2.8×** 速い  |
| Linux KVM    | ~150 µs pread miss | **mmap 1.4×** 速い | mmap 1.0×（同等） | **mmap 1.3×** 速い |

アクセスパターン（α）を何に変えても、**ストレージが遅い環境では mmap が常に上回り**、速い環境では LRU が常に上回ります。「hot set が RAM に収まる」「THP を有効にする」などの最適化は mmap の優位を 10–200× まで拡大します．

バッファプールの実装（LRU、eviction policy、スレッドセーフな競合制御など）は非自明なコードですが、mmap を使う限りそれは OS に丸投げできます。ストレージが遅い本番環境では、**その設計コストの省略がそのまま性能上の優位になります**。

## 2. 実験対象：2 つの実装

ベンチマークでは、同一のデータファイルと同一のアクセス列に対して次の 2 つの実装を比較します。ソースコードは [`bench.cpp`](bench.cpp) にあります。

### mmap パス（OS 委任型）

```
mmap(MAP_SHARED) でファイル全体を仮想アドレス空間にマップし、
madvise(MADV_RANDOM) でランダムアクセスをヒントとして設定する。
ページの fetch・eviction・aging はすべてカーネルの page cache に委任し、
アプリケーションはポインタの load 命令だけでデータにアクセスする。
```

- **hit 時:** 単なる `load` 命令 1 本。ページがすでに page cache にあれば仮想アドレスから直接読める。
- **miss 時:** page fault が発生し、カーネルがストレージから 4 KB ページを読み込む。スレッドはその間ブロックされる。
- **Linux 専用オプション:** `--huge-pages` を指定すると `madvise(MADV_HUGEPAGE)` を追加発行し、OS に 2 MB 大ページへの昇格（THP）を要求する。

### pread+LRU パス（アプリ管理型）

```
pread(2) に O_DIRECT (Linux) / F_NOCACHE (macOS) を設定することで
OS の page cache を完全にバイパスし、すべてのバッファ管理をアプリ内の
LRU（双方向リスト＋ハッシュマップ）で行う。
```

- **hit 時:** LRU のハッシュマップを引き、リストの先頭に移動するだけ（~1 µs 未満）。
- **miss 時:** `pread` syscall でストレージから直接読み込み、LRU へ挿入。LRU が満杯なら末尾エントリを evict する。
- **LRU 容量:** デフォルト 20,000 ページ = 80 MB（`--lru-pages` で変更可能）。
- **キャッシュの独立性:** `O_DIRECT` / `F_NOCACHE` のため、mmap パスの page cache 状態（warm/cold）に一切影響されない。

### 両パスに共通する実験設定

| 設定           | 値                                                       |
| -------------- | -------------------------------------------------------- |
| データファイル | 96 GB のランダムバイト列                                 |
| レコードサイズ | 4 KB（= OS ページサイズ）                                |
| アクセス分布   | Zipf 分布（α=1.0 が標準）                                |
| 測定操作数     | 1,000,000 ops（ウォームアップ 50,000 ops 除く）          |
| 出力形式       | JSON（スループット・レイテンシ%ile・キャッシュヒット率） |

#### Zipf 分布とアクセス列について

**Zipf 分布**はべき乗則に従うアクセス頻度分布で、「人気ランク k 位のページは 1 位のページの 1/k の頻度でアクセスされる」という特性を持ちます（α=1.0 のとき）。Web のページビューやデータベースのホットキーなど、現実の skewed アクセスをモデル化するために広く使われます。α が大きいほど少数ページへの集中度が増し、α が小さいほど一様分布（均等アクセス）に近づきます。

**アクセス列（Zipf 列）**とは、このZipf 分布から事前にサンプリングした「どのページ番号を読むか」のシーケンスです。本ベンチマークでは測定開始前に 1,050,000 個のページ番号を Zipf 分布でサンプリングし、cold・warm の両実験で同一のアクセス列を使って公平に比較します。α=1.0 のとき、この 1,050,000 サンプルが触れるユニークページ数は約 430,000 ページ（≈ 1.7 GB）です。残る約 620,000 回は既出ページへの再アクセスであり、これが LRU のキャッシュヒット率（≈ 50%）の源泉となっています。

## 3. 結果を読み解く鍵：ストレージレイテンシ

### 3.1 4 種類のアクセスコスト

mmap と pread+LRU のどちらを使っても、実際に発生するアクセスは以下の 4 種類だけです。2 台の環境で計測したコストを並べると、決定的な違いが見えてきます。

```
操作                         macOS (M4 Pro)    Linux (Xeon KVM)
─────────────────────────────────────────────────────────────────
mmap — page cache hit         ~0.04 µs          ~0.2 µs
mmap — page fault (cold)      ~100  µs          ~166  µs
pread+LRU — LRU hit           ~0.7  µs          < 1   µs
pread+LRU — pread miss        ~1    µs          ~150  µs
                                  ↑                   ↑
                             Apple Fabric SSD    KVM 仮想ブロック
                             (世界最速クラス)    (汎用仮想化層)
```

まず，キャッシュヒットした際はどの環境でも `mmap` のほうが早いです．これは `mmap` が単純にページの仮想アドレスから直接読み込むだけなのに対し、`pread+LRU` はハッシュマップのルックアップとリストの更新が必要なためです．
そして，**pread miss のコストには環境で 150 倍の差があります**。mmap の hit コストや page fault のコストはそれほど変わらないのに対し、LRU が miss したときの pread コストが環境によって大きく異なります。これが全ての結果の差を生んでいます。

### 3.2 単純なコストモデルで見る

Zipf α=1.0, LRU hit 率 ≈ 50% の条件で、1M 回の操作コストを概算してみましょう：

```
pread+LRU の合計コスト:
  = 500,000 × t_lru_hit  +  500,000 × t_pread_miss

  macOS: = 500K × 0.7µs  +  500K × 1µs   =  0.35s + 0.5s  = 0.85s → ~1.2M ops/s ✓
  Linux: = 500K × 0.7µs  +  500K × 150µs =  0.35s + 75s   = 75.4s →   ~13K ops/s ✓

mmap（cold）の合計コスト:
  = 500,000 × t_mmap_hit  +  500,000 × t_page_fault

  macOS: = 500K × 0.04µs  +  500K × 100µs  = 0.02s + 50s  = 50s → ~20K ops/s ✓
  Linux: = 500K × 0.2µs   +  500K × 166µs  = 0.1s  + 83s  = 83s → ~12K ops/s ✓
```

macOS では `t_pread_miss (1µs) ≪ t_page_fault (100µs)` であり、LRU は miss しても安いため圧倒的に有利です。  
Linux では `t_pread_miss (150µs) ≈ t_page_fault (166µs)` となり、両者のミスコストがほぼ揃います。その結果、hit 時のわずかなコスト差（mmap 0.2 µs < LRU ~1 µs）が積み重なり、mmap が僅差で上回ります。

## 4. 実験サマリー

### 4.1 cold ベースライン（Zipf α=1.0, LRU hit 率 ≈ 50%）

| 指標              | macOS               | Linux            |
| ----------------- | ------------------- | ---------------- |
| **mmap**          | 37,950 ops/s        | 18,545 ops/s     |
| **pread+LRU**     | **1,800,486** ops/s | **13,148** ops/s |
| 勝者              | LRU **47×**         | mmap **1.4×**    |
| pread miss コスト | ~1 µs               | ~150 µs          |

cold ベースラインは，ページキャッシュをwarmupしていない状態での測定です．
macOS では pread miss が非常に安いため、LRU が圧倒的に有利です。
Linux (KVM) では pread miss と page fault のコストが近いため、mmap が性能で上回ります。

### 4.2 warm（測定に使うアクセス列を事前に走査してページテーブルを温めた状態）

| 指標          | macOS                | Linux               |
| ------------- | -------------------- | ------------------- |
| **mmap**      | **16,967,270** ops/s | **4,356,687** ops/s |
| **pread+LRU** | 1,950,081 ops/s      | 13,251 ops/s        |
| 勝者          | mmap **8.7×**        | mmap **329×**       |

warm 実験は，**事前走査（prefault）** を行う実験です．本計測の前に、アクセスするページ列を先頭から末尾まで一通り走査します。mmap の場合、各ページへの初回アクセスで page fault が発生し、OS がストレージからページを RAM に読み込みながら**ページテーブルエントリ（PTE）を作成**します。
96 GB 全体を読み込むわけではなく、Zipf 列が触れる約 430,000 ページ（≈ 1.7 GB）だけが RAM に載ります。つまり，「これからアクセスするページはすでに既知」という想定です．page fault は 0 回となり、全アクセスが TLB ヒット → DRAM ロードだけで完結します。

性能評価の結果，mmap が大差をつけました．
pread+LRU の性能は cold と全く変わりません（macOS: 1.95M vs 1.80M、Linux: 13.3K vs 13.1K）。`F_NOCACHE` / `O_DIRECT` により LRU は page cache を利用できないため、ページテーブルが温まっても LRU は恩恵を受けられません。warm で mmap が大きく有利に見えるのは、**mmap だけが PTE の恩恵を受けられる**という構造的な非対称が原因です。

### 4.3 hot set サイズスイープ

| hot set              | macOS mmap | macOS LRU  | macOS 勝者 | Linux mmap | Linux LRU | Linux 勝者 |
| -------------------- | ---------- | ---------- | ---------- | ---------- | --------- | ---------- |
| 80 MB（= LRU 容量）  | 6,705,338  | 11,470,773 | LRU 1.7×   | 563,651    | 293,836   | mmap 1.9×  |
| 800 MB（LRU の 10×） | 208,542    | 3,227,164  | LRU 15×    | 60,739     | 25,996    | mmap 2.3×  |
| 8 GB（LRU の 100×）  | —          | —          | —          | 26,885     | 16,613    | mmap 1.6×  |
| 96 GB（全体）        | 37,950     | 1,800,486  | LRU 47×    | 18,545     | 13,148    | mmap 1.4×  |

hot set とは，データファイルの中でアクセスされるページを制限するオプションです．
これを指定すると，アクセス対象が96GBのファイル全体から「先頭Nページ」に制限されます．
warmupは行っていません．

macOS では hot set が広がるほど LRU の優位が拡大します（pread miss が安いため、miss が増えても痛くない）。Linux では全サイズで mmap が上回っています（pread miss が高価なため、LRU hit 率の低下が直撃する）。

### 4.4 Transparent Huge Pages（Linux のみ）

THP（`madvise`）を適用すると 4 KB ページが 2 MB 大ページに昇格し、TLB エントリ数が 1/512 に削減されます。これを有効化した際の実験結果です．

|         | hot set | mmap (THP なし) | mmap + THP    | THPの効果          |
| ------- | ------- | --------------- | ------------- | ------------------ |
| cold    | 96 GB   | 18,545          | **2,558**     | **0.14×（劣化）**  |
| warm    | 96 GB   | 4,356,687       | **2,509**     | **0.001×（壊滅）** |
| hot set | 80 MB   | 563,651         | **7,408,076** | **13×**            |
| hot set | 800 MB  | 60,739          | **5,174,393** | **85×**            |

```
THP が有効な条件: hot set ≪ RAM
  80 MB hot set → 2MB 大ページ 40 枚に収まる（L2 TLB の範囲内）
  → ページテーブルウォークが消え、純粋な DRAM 帯域で動作

THP が逆効果な条件: hot set ≈ RAM 以上
  96 GB ファイル on 16 GB RAM → khugepaged が compaction を試み続ける
  → p95 が 166 µs → 2,578 µs に悪化（compaction stall）
```

すなわち，THPは hot set が RAM に収まる場合に大きな効果を発揮します．

### 4.5 Zipf α スイープ（アクセス局所性依存性の検証）

「勝者はアクセスパターンで変わるか」を検証するため、モデルワークロードの局所性（α）を 0.5−1.5−2.0 と変化させた。

| α   | macOS mmap | macOS LRU  | **macOS 勝者** | Linux mmap | Linux LRU | **Linux 勝者** |
| --- | ---------- | ---------- | -------------- | ---------- | --------- | -------------- |
| 0.5 | 10,327     | 858,954    | **LRU 83×**    | 6,973      | 6,728     | **mmap 1.04×** |
| 1.0 | 30,673     | 1,509,377  | **LRU 49×**    | 18,095     | 13,174    | **mmap 1.37×** |
| 1.5 | 862,258    | 14,102,068 | **LRU 16×**    | 501,487    | 435,153   | **mmap 1.15×** |
| 2.0 | 8,869,359  | 24,942,943 | **LRU 2.8×**   | 3,532,055  | 2,736,168 | **mmap 1.29×** |

α（アクセス局所性）が変わっても、**勝者の順位は現境で完全に決まったまま変わらない**。macOS では常に LRU、Linux では常に mmap が勝つ．これは「ストレージレイテンシが負けまたは勝ちの構造的原因でり、局所性（ヒット率）はその差の大小を変えるのみ」であることを実測で裏付けする。

### 5.1 競争力を左右する 2 軸

実験全体を振り返ると、mmap と LRU の優劣は主に 2 つの軸で決まることがわかります。

**軸 1：ストレージレイテンシ**

pread miss のコストが page fault のコストに近づくほど、mmap の「hit が速い」優位が表面化します。

| ストレージ                            | pread miss コスト | page fault コスト | 傾向                            |
| ------------------------------------- | ----------------- | ----------------- | ------------------------------- |
| 最新世代 NVMe（< 5 µs）               | ≪ page fault      | —                 | **LRU 有利**（miss しても安い） |
| オンプレ NVMe SSD（~50–100 µs）       | ≈ page fault      | —                 | **拮抗**（ケース依存）          |
| クラウド VM / 仮想ブロック（~150 µs） | ≈ page fault      | ~166 µs           | **mmap 有利**                   |
| HDD（~10 ms）                         | ≫ page fault      | —                 | **mmap 有利**                   |

**軸 2：hot set と RAM の比率**

hot set が RAM に収まるほど page cache hit 率が上がり、mmap の「load 命令だけ」という速さが活きます。

| hot set / RAM             | mmap の状態             | 傾向                                                   |
| ------------------------- | ----------------------- | ------------------------------------------------------ |
| ≪ 1（例: 800 MB / 16 GB） | ほぼ常に page cache hit | **mmap が圧倒的に有利**（THP 併用で最大 200×）         |
| ≈ 0.5–1                   | hit と fault が混在     | **拮抗〜mmap 有利**                                    |
| ≫ 1                       | cold fault が連発       | **LRU が有利**（明示的 eviction で miss を制御できる） |

### 5.2 FaultKV が期待できる条件

以下の条件が揃うとき、FaultKV は LRU に対して 10× 以上の差をつけられます：

1. **hot set が RAM の数分の 1 以下に収まる**（working set が RAM-resident）
2. **ストレージレイテンシが > 10 µs 程度**（クラウド VM・HDD など）
3. **Linux で `madvise(MADV_HUGEPAGE)` を使う**（hot set を 2 MB 大ページに昇格し TLB 圧力を削減）
4. **長期稼働プロセス**（cold start 後、page table に hot ページが積み上がった steady-state）

実測での裏付け：

```
hot set 800 MB（RAM 16 GB の 5%）+ THP（Linux KVM 環境）:
  mmap: 5,174,393 ops/sec
  LRU:     26,057 ops/sec
  → mmap が 199× 速い
```

### 5.3 FaultKV が不向きな条件

- **Apple Silicon Mac やハイエンド NVMe 環境**（pread miss が ~1 µs と非常に安く、LRU が cold 状態でも圧倒的に有利）
- **cold start が頻繁な環境**（Kubernetes での頻繁な Pod 再起動など、steady-state に達する前に再起動される）
- **working set が RAM を大幅に超え、かつアクセスが均一に分散している**（ほぼ全操作が cold fault になる）
- **THP を `always` モードで設定している環境**（working set が大きい場合に compaction stall が発生するリスク）

## 6. まとめ

「OS の仮想メモリ機構はユーザランド LRU に比べて競争力があるか？」という問いに対して、実測からは次の答えが得られました。

> **競争力があるかどうかは、ストレージのレイテンシと hot set の大きさによって大きく変わります。**

| ストレージ速度                    | hot set / RAM      | OS mmap の競争力                                                 |
| --------------------------------- | ------------------ | ---------------------------------------------------------------- |
| 遅い（> 50 µs、クラウド VM・HDD） | RAM に収まる       | **十分にある**（THP 併用で LRU の 10–200×）                      |
| 遅い                              | RAM を大幅に超える | **拮抗〜やや劣る**（cold fault が連発するが LRU の miss も高価） |
| 速い（< 5 µs、最新 NVMe）         | どのサイズでも     | **乏しい**（pread miss が安いため LRU が有利）                   |

FaultKV はクラウド環境のような「本番のストレージは遅い」という前提のもとで設計されています。開発機（Apple Silicon）で mmap が LRU に見劣りするのは、その SSD が例外的に高速すぎるためです。本番のクラウド VM では逆の結果が得られることが実測で確認されており、FaultKV の設計方針はデプロイ対象の環境に整合していると言えます。
