# VMemKV Implementation Plan & Remaining TODO List

This document outlines the roadmap to implement the full, robust architecture of VMemKV based on the academic specifications (HLD/LLD), supporting both disk-efficient In-place updates and crash-resilient Write-Ahead Logging (WAL).

---

## 3. Startup Swap Validation Check
* **Status**: 🔴 **Not Implemented**
* **Objective**:
  - Implement a startup check in the main application / VMemKV initialization to verify that the system has an active Swap file of sufficient capacity (e.g., at least 64GB / 1TB on production environments) to prevent OOM Killer.

## 4. Profile the full-stall during a T2 rebuild (do_t2_rebuild=true)
* **Status**: 🟢 **Resolved (2026-08-16)**, mechanism since superseded (2026-08-19) -- the pre-redesign pathology was fixed first (confirmed via local A/B), then the deeper LTM-scale root cause (O(N) full-corpus copy) was eliminated by unifying `checkpoint()`/`defragment()` onto a reflink + hole-punch `checkpoint_and_defragment()` mechanism (O(diff) per cycle, verified on real XFS). Direct measurement then showed `dead_range_punch` (48% of cycle time) and `fsync` (36%) dominated, with T1 reorganize only 3.6% -- and separately, that `FALLOC_FL_PUNCH_HOLE` reclaims nothing below the filesystem block size, making the punch step ineffective for the project's typical small-value workloads regardless of cost. `checkpoint()`/`defragment()` were split back apart: `checkpoint()` is now `checkpoint_internal()`, an in-place `pwrite()` of the live tail to its own existing T2 offsets (no reflink, no relocation, works on any filesystem); `defragment()` is currently a T1-only placeholder with no T2 compaction implementation (see `docs/specification/low_level_design.md` 4.3-4.4, 5.2). See git history for the reflink-era design/validation record this entry originally described.
* **Original concern**:
  - `benchmark_results/2026073000/ycsb_e_timeline_in_memory_VMemKV-Bloom-Simd-T1InlineValue_Bloom-Simd-T1InlineValue_8B.json` showed total ops (scan+insert) dropping to exactly 0 for one full second around a `t2_reorg_ops=1` event, under the pre-redesign implementation.
* **Local measurement (in-memory scale, standalone harness, not committed -- see session notes)**: 1M keys x 1KB values, `VMemKVStore` (all-opts config), 4 GET threads + 4 UPDATE threads hammering continuously, `defragment()` triggered mid-run, throughput sampled at 100ms granularity. Built the pre-redesign implementation (commit `d4aa17f`) in a separate worktree for a true A/B comparison against the current code:
  - **Current (post-redesign)**: `defragment()` completed in **10.4s**, and combined throughput showed **no observable dip at all** during the entire rebuild window (stayed at ~280-350K ops/100ms throughout, same as baseline) -- confirmed reproducible across 3 independent runs.
  - **Pre-redesign** (`d4aa17f`, same workload): `defragment()` took **409.8s** (~39x longer) to return, and combined throughput dropped to **exactly 0 within 2.4s of starting** and stayed at 0 for the rest of the observed window (12.5s; the actual stall may have covered most of the full 409.8s).
  - Root cause of the old pathology: the pre-redesign convergence loop (`while (true) { t1_.reorganize(...); if (t1_.append_size() == 0) break; }`) had to repeatedly re-sweep new entries created by the *concurrent* write stream (each ScanBaseSequential out-of-place update adds a fresh append-region entry), which under sustained heavy writes could take far longer to converge than a single pass. The redesign's fixed two-pass structure doesn't have this open-ended re-sweep, eliminating the stall as a side effect of the exception-safety fix.
* **AWS LTM-scale measurement (i4i.2xlarge, real NVMe, 2026-08-15)**: same idea at the *actual* LTM corpus scale used by the real benchmark matrix -- 1KB values, ~8.26M keys (~7GB), the project's real LTM cgroup budget (`MemoryHigh=1GiB`/`MemoryMax=2GiB`/`MemorySwapMax=1TiB`, `target_ratio=8.0`, matching `benchmark_matrix.sh`'s `ltm_memory_budget_bytes()`/`scenario_env_prefix ltm` exactly). Population/checkpoint ran *unconstrained* first (not what's being measured), then only the timed workload + `defragment()` ran under the real cgroup:
  - Unconstrained baseline: bulk_load 8.8s, first checkpoint (= a full T2 rebuild, ~7GB) 42.4s. So purely CPU/I/O-bound, a ~7GB rebuild is fast (~6s/GB).
  - Under the real 1GiB/8x cgroup budget: opening the existing 7GB store alone took 21.5s, and a `defragment()` triggered at t=20s **had not returned after 27+ minutes** (~40x+ slower than the unconstrained baseline) when the run was stopped.
  - Confirmed via `gdb -p <pid> -batch -ex "thread apply all bt"` on the live AWS instance that this is **not a hang/deadlock**: the thread was caught mid-`write()` syscall inside the copy loop, i.e. genuinely making forward progress, just extremely slowly. `memory.stat` showed `pgscan_direct=26.4M`, `pgsteal_direct=7.5M`, `workingset_refault_file=4.4M` -- classic severe thrashing (the same pages being reclaimed and refaulted repeatedly), consistent with a corpus 8x larger than the resident budget and no useful locality to exploit during a near-random full-corpus scan.
* **Open question this raises**: the `target_ratio=8.0` / `MemoryHigh=1GiB` combination is the *same* one the existing AWS benchmark matrix already uses for its official LTM scenarios (`vmemkv_matrix::scenario_env_prefix ltm`) -- so if `defragment()`/a full T2 rebuild is *ever* triggered during a real LTM/1KB run (naturally via `space_amp_over_threshold()`, or via an explicit trigger added to YCSB-E), it could plausibly take on this same order of magnitude (many minutes, not seconds), which no reasonably-sized benchmark window (30-60s) could ever observe completing. This would also retroactively explain why the original YCSB-E finding above never recovered within its 30s window -- not necessarily because reads/writes were blocked by a lock, but because the auto-triggered rebuild itself may never have gotten anywhere close to finishing.
* **Not a regression -- confirmed against pre-existing data (2026-08-15)**: `benchmark_results/2026081313/reorg_scaling_ltm_1KB.jsonl` (dated *before* this session's `rebuild_t2_and_maybe_checkpoint()` redesign) already shows the identical corpus scale (`key_count=8259552`, the same real LTM `ratio=1.0`/`target_ratio=8.0` config) failing to finish the `t1t2` (full T2 rebuild) probe within its 60s internal cap, timing out. Smaller ratios (0.25/0.5/0.75 -> 2/4/6GB) completed in a roughly linear 20.4s/30.9s/47.4s (~8-10s/GB) -- the cliff appears specifically once the live corpus reaches the full 8x-budget scale, both before and after today's changes. This is a pre-existing, previously-unflagged characteristic of full-scale T2 rebuilds under the project's own declared LTM memory ratio, not something introduced today.
* **Architecturally expected**: `defragment()` is currently an O(N) full-corpus copy regardless of how much garbage actually needs reclaiming, so this scaling cliff under severe memory pressure (corpus >> resident budget, no reusable locality during a near-random full scan) is the expected consequence of that design, not a bug to fix in isolation.
* **Resolved (2026-08-16)**: option (c) was pursued -- the incremental-defrag redesign (reflink-clone + hole-punch, unified into `checkpoint_and_defragment()`) attacked the root cause directly and eliminated the scaling cliff; see git history for the full design/validation record (this item's former item 5 entry).

## 5. Scan-side offset-order read reordering (no storage compaction)
* **Status**: 🔴 **Not Implemented** -- proposed idea, not yet designed in detail or built.
* **Motivation**: Direct measurement (2026-08-20, standalone harnesses, not committed) established that Scan throughput is dominated by whether a read goes through T2's base region (seqlock-free, `MADV_SEQUENTIAL`, pre-warmed) or its tail region (seqlock-protected, `MADV_RANDOM`) -- a fully tail-resident 500K-key/200B-value corpus scanned in ~0.13s versus ~0.007s base-resident with zero churn (~18x), and even a heavily out-of-place-scattered base-resident corpus (10-40% churned) still scanned in 0.02-0.035s, 3-6x faster than pristine tail. Separately, an 8M-key lifecycle measurement showed a full from-scratch rewrite costs ~19.7s (~2.46us/key) while realistic concurrent write throughput (13,958 ops/sec measured at 32 threads on a 20-core machine) degrades Scan below 80% of baseline in well under a second -- a corpus-size-independent argument (both costs scale linearly with corpus size) that periodic full-rewrite compaction cannot keep up with sustained writes above roughly 4,000 ops/sec.
* **Idea**: Scan already reads in bounded batches (~100 records per call, per `BaseReader::kScan`'s own comment). Within one batch, sort the batch's candidates by *T2 physical offset* before reading them (instead of reading in T1's key order), then re-sort the fetched results back to key order before invoking the caller's callback. This targets the actual mechanism behind the churn-driven slowdown (key order and physical offset order decorrelating after out-of-place writes) without moving any storage bytes -- no writer-stop, no space reclaimed, purely a Scan-internal read-ordering change.
* **Known limitation**: does not address space amplification on its own -- purely a Scan-internal read-ordering change, no storage bytes move, no space reclaimed.
* **Superseded (2026-08-20)**: rather than pairing this idea with the block-level evict+punch complement originally sketched below, `defragment()` was implemented directly as a full relocating rewrite (`defragment_internal()`, `docs/specification/low_level_design.md` 4.6) -- every live T2 record is re-copied to a fresh file in T1's key order. This is the superset of both ideas: it restores the same key-order/physical-offset correlation this item's scan-side reordering targets, *and* reclaims 100% of dead space (the file is replaced wholesale, so `FALLOC_FL_PUNCH_HOLE`'s block-granularity failure mode -- see item 4 -- never applies). Cost scales with live corpus size, so it is not cheap enough to run on every cycle; it is `Force`-triggered only (no automatic threshold trigger wired up yet). The block-evict+punch idea below remains a possible cheaper, space-only complement if `defragment()`'s O(corpus) cost ever proves too coarse-grained in practice, but is not needed for the current implementation.
* **Original idea (space-only complement, not built)**: evacuate live entries out of a heavily-fragmented 4KB-aligned block via ordinary out-of-place writes (the same per-key `T1Index::put()` redirect already used for other out-of-place updates, not a full T1 reorganize), then `fallocate(FALLOC_FL_PUNCH_HOLE)` the now-100%-dead, block-aligned range -- sized specifically to satisfy `FALLOC_FL_PUNCH_HOLE`'s block-granularity requirement (see item 4's finding that sub-block punches reclaim nothing).

## 6. LTM full-corpus checkpoint()/write-path stalls under severe memory pressure (found 2026-08-28)
* **Status**: 🟡 **Root-caused as thrashing, not a code bug** -- same underlying class of pathology as item 4 above, now confirmed to also hit the ordinary write path and `checkpoint_internal()`'s durabilization pwrite/msync, not just a full T2 rebuild. No commit-level fix applies; see Implications below.
* **Symptom**: `run_maintenance_contention_probe.sh`'s `checkpoint_contention`/`reorg_contention` spot checks (full corpus, 32 concurrent writer threads, LTM cgroup) hang completely for both `ltm/1KB` and `ltm/64KB`, hitting the probe driver's 300s outer timeout with zero measured output. `run_defrag_scaling_probe.sh`'s LTM sweep and `run_checkpoint_throughput_probe.sh`'s `ltm/1KB`/`ltm/64KB` points show the same pattern at full/near-full corpus. `benchmark_results/2026082101` (git revision `4a7084c`) recorded these same points completing in 5.2-5.68s that round.
* **Confirmed NOT caused by the 2026-08-28 checkpoint-auto-trigger-fix session** (`6aec324`/`db31a6b`/`a3bb115`): an AWS A/B (i4i.8xlarge, real 1GiB LTM cgroup, `ltm/1KB checkpoint_contention`) comparing `bc9bfd2` (HEAD immediately before that session's first commit) against `a3bb115` (HEAD after all three of that session's commits) showed **identical behavior**: both hit the 300s outer timeout with zero output.
* **Bisect attempt abandoned as inapplicable**: walked backward through the 5 candidate commits between `4a7084c` and `bc9bfd2` (`586f067`, `b196984`, `47a2178`, `35936d7`, `8dc60f7`) -- every one reproduced the hang, including **`4a7084c` itself**, the exact commit `benchmark_results/2026082101` was built from. Re-tested `4a7084c` three ways to rule out an environment mismatch before concluding this: (1) the probe's own real 600s outer timeout instead of an abbreviated 120s, (2) an AMI pinned to the exact kernel recorded in that report's context (`6.17.0-1019-aws`) rather than whatever AMI a fresh `describe-images` query resolves to today, (3) `MemorySwapMax` corrected to the real `1TiB` (`vmemkv_matrix::ltm_swap_budget_bytes()`) after finding an earlier manual repro had been under-provisioning it at `16GiB`. All three still hung. Since the literal commit the "good" numbers came from can't reproduce them under matching conditions, there is no introducing commit to bisect to -- the numbers in that report were a favorable outcome of an inherently high-variance stress test, not a stable baseline a later commit regressed away from.
* **Direct gdb confirmation (2026-08-28), `4a7084c`, matching kernel/swap-budget/probe args**: launched `bench_kv` as gdb's own child (`ptrace_scope=1` blocks attaching to an unrelated PID) inside the real LTM `systemd-run` cgroup wrap, `SIGINT` after 3.5 minutes stuck at 2.9s CPU time (i.e. blocked, not spinning), `thread apply all bt`:
  - Main thread: `reorg_probe::run_steady()` -> `write_entry_lockfree()` -> `T2FlatFile::append_default()`, stuck inside the record-copy `memcpy` -- the *ordinary write path*, not checkpoint at all.
  - `reorg_worker_` thread: auto-triggered `checkpoint_internal()` (at this revision, still the pre-`586f067` `pwrite()`-per-record durabilization design, not the later `msync()` design) stuck inside `pwrite64()`.
  - Both threads are doing genuine, correct work; both are just extremely slow. This is architecturally the same "8x-oversubscribed corpus, near-random access, no reusable locality" thrashing item 4 already documented for the old T2-rebuild path (`pgscan_direct`/`pgsteal_direct`/`workingset_refault_file` churn), now confirmed to also hit `T2FlatFile::append_default()`'s ordinary append path and `checkpoint_internal()`'s own durabilization write -- i.e. this is a property of the storage design under `target_ratio=8.0`, not a bug specific to any reorg-family operation or any one commit.
* **Repeated at HEAD (`c13fe40`, msync()-based checkpoint_internal(), same kernel/cgroup/probe args) -- pinpointed the actual mechanism**: `gdb` (launched the same way, as bench_kv's own child) itself got stuck for 9+ minutes inside `mem_cgroup_handle_over_high()` (visible directly via `/proc/<pid>/stack`, no ptrace needed) just from touching its own ~67MB footprint -- a completely unrelated process, sharing only the cgroup. `bench_kv`'s own threads were independently caught mid-`exc_page_fault` the same way. Confirmed via the cgroup's `memory.pressure`: `full avg10=92.41 avg60=92.05 avg300=87.95` (PSI "full" -- *every* task in the cgroup stalled, not just some, for 92% of the preceding 10s/60s and 88% of the preceding 300s) while `memory.current` (1.12GB) was only ~12% over `memory.high` (1GiB) -- nowhere near `memory.max` (2GiB), so this isn't OOM-adjacent, it's `memory.high` throttling behaving exactly as designed under sustained direct-reclaim pressure. `memory.stat`: `pgscan_kswapd=0` / `pgscan_direct=1,322,992` -- *zero* background reclaim, 100% of the 1.3M+ pages scanned so far went through synchronous direct reclaim in whichever thread's fault path triggered it. This reframes the finding: it isn't that `fdatasync()`/`pwrite()`/`msync()`/`memcpy()` are each individually slow under I/O contention -- any of them can be the one a given thread happens to be inside when `mem_cgroup_handle_over_high()`'s throttle catches it, because the mechanism operates on *any* memory-touching operation from *any* task in the cgroup once usage is sustained over `MemoryHigh`, indiscriminately of which VMemKV code path (or, as gdb's own stall shows, even non-VMemKV code) triggered it.
* **Implication for `benchmark_results/2026082819`'s CRUD/YCSB matrix**: unlike the previous entry's scope note claimed, this is *not* confined to the auxiliary probes -- `results_ltm_1KB.json`'s Insert/Update throughput also dropped substantially versus `2026082101` (Update: -60 to -86% across all VMemKV variants, Insert: -28%), consistent with the same thrashing now being hit more often by the ordinary CRUD matrix's own write path once `checkpoint_internal()` actually auto-triggers during a run (see item this session's checkpoint-trigger fix addressed). Any conclusion about the MAP_SHARED-vs-MAP_PRIVATE design question, or checkpoint-frequency tuning, drawn from `2026082819`'s LTM numbers should be treated as provisional until this is understood better -- see Next steps.
* **Literature confirms this is a known, general Linux/cgroup-v2 characteristic, not VMemKV-specific**: a 2020 mm/memcg patch from Johannes Weiner (kernel maintainer) -- ["mm: memcontrol: asynchronous reclaim for memory.high"](https://lore.kernel.org/linux-mm/20200219181219.54356-1-hannes@cmpxchg.org/) -- describes the exact symptom in its own commit message: *"cgroup limits inject direct reclaim stalls into the workload where previously all reclaim was handled by kswapd."* By default, `memory.high` has **no dedicated background reclaimer for the offending cgroup** -- global kswapd only acts on node-wide watermarks and has no reason to help a single over-budget cgroup while the rest of the host (247GB here) is idle; every cgroup over its own `memory.high` is on its own, via synchronous reclaim in the allocating thread. That patch adds an async reclaimer, but only inside `memory.high`'s ~4% "grace buffer" -- beyond that it falls back to the same direct-reclaim-and-throttle path. Separately, cgroup v2's writeback *is* memcg-aware (`wb_domain`, per-cgroup `balance_dirty_pages()`) -- so this isn't the older cgroup-v1-era "dirty pages triggering premature OOM" bug -- but memcg-aware writeback only regulates the *rate* of dirtying; it does nothing once the live working set itself exceeds the budget.
* **`target_ratio` sweep (2026-08-28) -- the "8x oversubscription" framing was wrong**: swept `VMEMKV_BENCH_TARGET_RATIO` from `8.0` down to `1.0` (i.e. corpus sized to *exactly* match, not exceed, the 1GiB `memory.high` budget), same `t1t2_steady`/`ltm/1KB` probe, 180s cap per point. **Every single ratio hung the full 180s, including `1.0`.** Live-observed the `1.0` run: `memory.current` reached ~100% of `memory.high` within 8s (populate finishing, expected), crept to ~105% by 30s and ~108% by 90s -- and CPU time consumed by the process **stopped increasing entirely between the 30s and 90s marks** (0 progress for 60 straight seconds) while `memory.pressure`'s `full avg10` climbed from 69 to 98. This is not a magnitude-dependent cliff -- it's a **runaway spiral that both matches the literature above and this specific write-heavy access pattern**: `t1t2_steady` keeps dirtying fresh pages (bulk_load, then WAL-durable churn) faster than the *only* available reclaim path (synchronous, in the same throttled threads) can catch up, so crossing `memory.high` even by single-digit percent, under continuous write pressure and zero background reclaim, does not self-correct -- it compounds. The oversubscription ratio changes how much *headroom* there is before the first crossing, not whether the crossing is recoverable once it happens.
* **Dirty-page hypothesis directly tested and refuted (2026-08-28)**: proposed mechanism was "un-durabilized T2 bytes accumulate faster than checkpoint/writeback can flush them, so reclaim hits expensive dirty pages." Polled the `ltm/1KB target_ratio=1.0` repro's cgroup `memory.stat` every 5s (`file`, `anon`, `file_dirty`, `file_writeback`) through the onset of the stall. **`file_dirty` never exceeded 64KB and dropped to 0 once the stall began -- dirty file pages are not the bottleneck.** Instead: `file` (T2's own file-backed pages) collapsed from ~175MB to single-digit MB between t=20s and t=30s (the kernel evicting essentially all of T2's clean resident data under pressure), while `anon` grew continuously and without bound over the same window (889MB at t=15s -> 1107MB+ by t=40s, still climbing when killed) -- confirmed independently via `/proc/<pid>/smaps_rollup` on the live stalled process: `Pss_Anon: 1,115,976 kB` vs `Pss_File: 1,517 kB` (99.9% of RSS is anonymous, not T2's mmap at all). **The actual driver is unbounded anonymous (heap) memory growth, not T2's page cache or its dirty-page backlog.** This also means checkpoint-frequency-based mitigations (this whole item's original framing) address the wrong axis entirely -- checkpoint only affects T2's file-backed pages, which turn out not to be the problem.
* **Malloc-arena-fragmentation hypothesis tested and refuted**: the anon growth's shape (repeated ~128MB `rw-p`/`00:00`-backed VMAs in `/proc/<pid>/smaps`) looked like classic glibc multi-threaded arena bloat, and `bench_kv.cpp`'s own `make_key()`/`make_value_for_key()` helpers do allocate a fresh heap `std::string` per call in tight loops (`bulk_load_impl()` single-threaded over the full corpus; the churn loop concurrently across up to 16 threads) -- a plausible contributor. Re-ran the identical repro with `MALLOC_ARENA_MAX=1` (forces one shared arena, eliminating per-thread arena fragmentation as a variable): **still hung the full 150s.** Rules out arena-count fragmentation as the sole or primary cause; the anon growth is either genuine (VMemKV's own live in-memory structures, e.g. T1's sorted region, growing larger than expected) or a single-arena allocator pathology (fragmentation/non-decommit within one arena) rather than a multi-arena one.
* **Root cause found and verified (2026-08-29): `T1Index::AppendRegion`'s fixed-capacity open-addressed hash table becomes ~100% resident from a small fraction of it being touched.** `T1AppendCapacityLog2 = 22` (`include/vmemkv/config.hpp:88`) gives `APPEND_CAP = 2^22 = 4,194,304` slots; compiled and measured `sizeof(AppendSlot) = 56` bytes (`T1IndexT::APPEND_SLOT_SIZE`, confirmed via a real build against `vmemkv::Config<>`, not assumed) -- so every `new AppendRegion()` (`t1_index.hpp:929`) reserves `4,194,304 * 56 = 234,881,024` bytes (**224 MB**) via `mmap(MAP_PRIVATE|MAP_ANONYMOUS|MAP_NORESERVE)`, unconditionally, regardless of actual corpus size. `t1_.reorganize()` allocates a **brand-new** `AppendRegion` on every cycle (`next_active_region = new AppendRegion()`, `t1_index.hpp:529`) and only frees the old one after its EBR grace period (`delete old_active_gen->region`, `t1_index.hpp:661`).
  Reproduced the mechanism **locally, without AWS**, in an ~80-line standalone probe (`/tmp/scatter_probe.cpp`): mmap'd a real 224 MB region, inserted 258,000 entries (the `ltm/1KB`/`ratio=1.0`/`churn-ratio=0.25` workload's actual churn count) via open addressing with a uniform-random hash (matching `AppendSlot`'s access pattern) and `memset()`'d each touched slot (56 bytes) as a real insert would. Measured via `/proc/self/status` `VmRSS`:
  ```
  region_bytes=234881024 (224.0 MB)
  RSS after mmap (reserve only): 3632 kB
  inserts=258000 collisions=8494 load_factor=0.0615
  RSS after 258000 scattered inserts: 231156 kB
  ```
  **At only 6.15% load factor, 98.4% of the 224 MB region became resident.** This is the birthday-paradox/coupon-collector effect: with slots landing pseudo-uniformly across `APPEND_CAP` and 56 bytes/slot << 4096-byte pages (~73 slots/page), even light occupancy touches nearly every page (`P(page untouched) = (1 - 73/4,194,304)^258,000 ≈ 1.1%`). This is a fully deterministic, occupancy-independent-above-a-low-threshold cost, not a probabilistic edge case.
  This single confirmed finding explains every observation from the dirty-page investigation above without needing any cgroup/reclaim-policy story: (1) unbounded, continuous anon growth under sustained churn -- each `reorganize()` cycle mints a fresh, near-fully-resident 224 MB region; if EBR reclaim of the *previous* generation lags the mint rate (readers still in-flight, or the reorg worker itself stalled by the very memory pressure this causes), multiple 224 MB generations pile up live at once, a genuine reinforcing feedback loop; (2) why `file` (T2) collapsed to near-zero while `anon` kept climbing -- the kernel cheaply reclaims clean file-backed T2 pages first, leaving increasingly anon-dominated (swap-costly) residency behind; (3) why this is **not** MAP_SHARED-, checkpoint-, or oversubscription-ratio-specific -- `AppendRegion` predates MAP_SHARED entirely and is untouched by checkpoint/defragment tuning; its cost is paid on every `reorganize()` cycle at any `target_ratio`, including `1.0`. **This also overturns the earlier "OS/cgroup swap-reliant architecture is fundamentally troubled" framing raised in discussion -- the mmap/swap design itself isn't at fault here; a specific, fixable T1 sizing choice is.**
* **`madvise(MADV_DONTNEED)`-ahead-of-`munmap()` option tested locally and refuted as a no-op (2026-08-29)**: hypothesis was that proactively decommitting a retiring `AppendRegion`'s pages before `munmap()` (in `~AppendRegion()`) would reclaim RSS faster/more reliably than relying on `munmap()` alone. Measured with a standalone probe (`/tmp/madvise_probe.cpp`, same 224MB/258K-scattered-insert setup as above), 3 runs, `/proc/self/status` `VmRSS` + `clock_gettime` around each call:
  ```
  [bare munmap]      rss_before=230328 kB rss_after=3576 kB   freed=226752 kB elapsed=7.8 ms
  [madvise+munmap]   rss_after_madvise=4156 kB (madvise=6.3ms) rss_after_munmap=4156 kB (munmap=0.01ms)
  [madvise, region still mapped, NOT unmapped] freed=227008 kB, mapping stays valid (reads back zeroed)
  ```
  **Bare `munmap()` alone already frees essentially the entire region synchronously in ~7-8ms -- adding `madvise(DONTNEED)` first changes nothing** (same total freed, same order-of-magnitude latency, `munmap()` itself then costs ~0ms since there's nothing left to do). The only place `madvise(DONTNEED)` does something `munmap()` can't is decommitting RSS from a region **that stays mapped** (case 3 above) -- but that's unsafe here: `append_immutable_`'s whole contract is that readers may still legitimately read a frozen-but-not-yet-EBR-cleared generation (`t1_index.hpp` `FreezableRegion`/EBR comments), and `MADV_DONTNEED` zeroes the underlying pages, i.e. destroys live data a reader could still observe -- not just a VM-bookkeeping hint. The only point at which `madvise`-ing is actually safe is exactly the point EBR already permits `delete`/`munmap()`, so it cannot be moved earlier than what already happens today. **Conclusion: option 3 is dead -- it doesn't reduce peak RSS during a live cycle (confirmed: `munmap()` isn't the slow part) and can't safely be applied any earlier than current `delete` timing (would require the same EBR-safety proof `delete` already waits for).** If a real lag exists between region retirement and reclaim, the fix has to target *how promptly EBR safety is reached / how promptly `reorganize()` runs*, not the decommit mechanism -- i.e. this pushes weight back onto (b) below and onto options 1/2.
* **`append_region_live_count`/`append_region_peak_count` instrumentation added (2026-08-29), item 4 above answered directly, no AWS needed**: added a live/high-water-mark counter for `AppendRegion` instances to `T1Index` (incremented/decremented at its 2 creation sites -- the constructor and `reorganize()` -- and its 2 destruction sites -- `reorganize()`'s post-EBR cleanup and `~T1Index()`), exposed via `VMemKVStatistics::append_region_live_count`/`append_region_peak_count`.
