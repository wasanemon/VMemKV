## 4. Profile the full-stall during a T2 rebuild (do_t2_rebuild=true)
* **Status**: 🟢 **Resolved (2026-08-16)** -- the pre-redesign pathology was fixed first (confirmed via local A/B), then the deeper LTM-scale root cause (O(N) full-corpus copy) was eliminated entirely by unifying `checkpoint()`/`defragment()` onto the reflink + hole-punch `checkpoint_and_defragment()` mechanism (O(diff) per cycle, implemented and verified on real XFS -- see the now-removed item 5's final state in git history for the full design/validation record).
* **Original concern**:
  - `benchmark_results/2026073000/ycsb_e_timeline_in_memory_VMemKV-Bloom-Simd-T1InlineValue_Bloom-Simd-T1InlineValue_8B.json` showed total ops (scan+insert) dropping to exactly 0 for one full second around a `t2_reorg_ops=1` event, under the pre-redesign implementation.
* **Local measurement (in-memory scale, standalone harness, not committed -- see session notes)**: 1M keys x 1KB values, `VMemKVStore` (all-opts config), 4 GET threads + 4 UPDATE threads hammering continuously, `defragment()` triggered mid-run, throughput sampled at 100ms granularity. Built the pre-redesign implementation (commit `d4aa17f`) in a separate worktree for a true A/B comparison against the current code:
  - **Current (post-redesign)**: `defragment()` completed in **10.4s**, and combined throughput showed **no observable dip at all** during the entire rebuild window (stayed at ~280-350K ops/100ms throughout, same as baseline) -- confirmed reproducible across 3 independent runs.
  - **Pre-redesign** (`d4aa17f`, same workload): `defragment()` took **409.8s** (~39x longer) to return, and combined throughput dropped to **exactly 0 within 2.4s of starting** and stayed at 0 for the rest of the observed window (12.5s; the actual stall may have covered most of the full 409.8s).
  - Root cause of the old pathology: the pre-redesign convergence loop (`while (true) { t1_.reorganize(...); if (t1_.append_size() == 0) break; }`) had to repeatedly re-sweep new entries created by the *concurrent* write stream (each ScanBaseSequential out-of-place update adds a fresh append-region entry), which under sustained heavy writes could take far longer to converge than a single pass. The redesign's fixed two-pass structure doesn't have this open-ended re-sweep, eliminating the stall as a side effect of the exception-safety fix.
* **AWS LTM-scale measurement (i4i.2xlarge, real NVMe, 2026-08-15)**: same idea at the *actual* LTM corpus scale used by the real benchmark matrix -- 1KB values, ~8.26M keys (~7GB), the project's real LTM cgroup budget (`MemoryHigh=1GiB`/`MemoryMax=2GiB`/`MemorySwapMax=1TiB`, `target_ratio=8.0`, matching `benchmark_matrix.sh`'s `ltm_memory_budget_bytes()`/`scenario_env_prefix ltm` exactly). Population/checkpoint ran *unconstrained* first (not what's being measured), then only the timed workload + `defragment()` ran under the real cgroup:
  - Unconstrained baseline: bulk_load 8.8s, first checkpoint (= a full T2 rebuild, ~7GB) 42.4s. So purely CPU/I/O-bound, a ~7GB rebuild is fast (~6s/GB).
  - Under the real 1GiB/8x cgroup budget: opening the existing 7GB store alone took 21.5s, and a `defragment()` triggered at t=20s **had not returned after 27+ minutes** (~40x+ slower than the unconstrained baseline) when the run was stopped.
  - Confirmed via `gdb -p <pid> -batch -ex "thread apply all bt"` on the live AWS instance that this is **not a hang/deadlock**: the thread was caught mid-`write()` syscall inside the copy loop, i.e. genuinely making forward progress, just extremely slowly. `memory.stat` showed `pgscan_direct=26.4M`, `pgsteal_direct=7.5M`, `workingset_refault_file=4.4M` -- classic severe thrashing (the same pages being reclaimed and refaulted repeatedly), consistent with a corpus 8x larger than the resident budget and no useful locality to exploit during a near-random full-corpus scan.
* **Open question this raises**: the `target_ratio=8.0` / `MemoryHigh=1GiB` combination is the *same* one the existing AWS benchmark matrix already uses for its official LTM scenarios (`vmemkv_matrix::scenario_env_prefix ltm`) -- so if `defragment()`/a full T2 rebuild is *ever* triggered during a real LTM/1KB run (naturally via `space_amp_over_threshold()`, or via an explicit trigger added to YCSB-E), it could plausibly take on this same order of magnitude (many minutes, not seconds), which no reasonably-sized benchmark window (30-60s) could ever observe completing. This would also retroactively explain why the original YCSB-E finding above never recovered within its 30s window -- not necessarily because reads/writes were blocked by a lock, but because the auto-triggered rebuild itself may never have gotten anywhere close to finishing.
* **Not a regression -- confirmed against pre-existing data (2026-08-15)**: `benchmark_results/2026081313/reorg_scaling_ltm_1KB.jsonl` (dated *before* this session's `rebuild_t2_and_maybe_checkpoint()` redesign) already shows the identical corpus scale (`key_count=8259552`, the same real LTM `ratio=1.0`/`target_ratio=8.0` config) failing to finish the `t1t2` (full T2 rebuild) probe within its 60s internal cap, timing out. Smaller ratios (0.25/0.5/0.75 -> 2/4/6GB) completed in a roughly linear 20.4s/30.9s/47.4s (~8-10s/GB) -- the cliff appears specifically once the live corpus reaches the full 8x-budget scale, both before and after today's changes. This is a pre-existing, previously-unflagged characteristic of full-scale T2 rebuilds under the project's own declared LTM memory ratio, not something introduced today.
* **Architecturally expected**: `defragment()` is currently an O(N) full-corpus copy regardless of how much garbage actually needs reclaiming, so this scaling cliff under severe memory pressure (corpus >> resident budget, no reusable locality during a near-random full scan) is the expected consequence of that design, not a bug to fix in isolation.
* **Resolved (2026-08-16)**: option (c) was pursued -- the incremental-defrag redesign (reflink-clone + hole-punch, unified into `checkpoint_and_defragment()`) attacked the root cause directly and eliminated the scaling cliff; see git history for the full design/validation record (this item's former item 5 entry).
