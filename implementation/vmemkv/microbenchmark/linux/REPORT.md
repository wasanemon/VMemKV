# VMemKV マイクロベンチマーク レポート (Linux)

## 0. テスト環境

| 項目         | 詳細                                                               |
| ------------ | ------------------------------------------------------------------ |
| マシン       | KVM 仮想マシン                                                     |
| CPU          | Intel Xeon Gold 6138 @ 2.00 GHz — 8 vCPU（1 コア × 8 ソケット）    |
| RAM          | 16 GB（スワップなし）                                              |
| ストレージ   | /dev/vda2（仮想ブロックデバイス, 120 GB）                          |
| OS           | Rocky Linux 9.3 (Blue Onyx), Kernel 5.14.0-362.18.1.el9_3.x86_64   |
| コンパイラ   | GCC 11.4.1 / C++20, `-O3 -march=native`                            |
| データセット | 96 GB ファイル（RAM の 6×）                                        |
| THP 設定     | `[always]`（OS が全 mmap 領域に対して 2MB 大ページを積極的に昇格） |

> **注意:** このマシンは KVM ハイパーバイザ上の仮想環境であり、ストレージアクセスは仮想ブロックデバイス越しに行われる。ランダム I/O レイテンシは ~150 µs であり、mmap の page fault コストとほぼ等しい。この特性がベンチマーク結果の傾向を大きく左右する。

---

## 1. 目的

VMemKV の中核仮説「OS の仮想メモリ機構（mmap + ページキャッシュ）はアプリケーション実装の LRU バッファプール（pread + explicit eviction）と競合しうるか？」を本環境（Linux KVM + Xeon）で実測で検証する。

---

## 2. 実験設計

### 2.1 比較対象

|                 | `mmap` path                             | `pread + LRU` path                            |
| --------------- | --------------------------------------- | --------------------------------------------- |
| バッファ管理    | カーネルの page cache に完全委任        | アプリ内 LRU（双方向リスト + ハッシュマップ） |
| OS cache bypass | なし                                    | `O_DIRECT` で page cache バイパス             |
| miss 時         | page fault → カーネルトラップ (~150 µs) | `pread(2)` syscall + I/O (~150 µs)            |
| hit 時          | 単なる `load` 命令 (~0.1–0.2 ns)        | ハッシュ引き + リスト操作 (< 1 µs)            |

> **本環境の特徴:** 仮想ブロックデバイスにより pread + O_DIRECT の miss コストが ~150 µs となり、mmap の page fault コスト（~166 µs）とほぼ等しい。この均等化が結果の傾向を決定づける（詳細は §5.1 参照）。

### 2.2 ワークロード

- **データセット:** 96 GB のファイルを `mmap(MAP_SHARED)` または `pread + O_DIRECT` でアクセス
- **レコードサイズ:** 4 KB（1 レコード = 1 OS ページ）
- **アクセスパターン:** Zipf 分布（α=1.0 が標準）
- **LRU バッファプール:** 20,000 ページ = 80 MB
- **測定操作数:** 1,000,000 ops（ウォームアップ 50,000 ops を除く）

### 2.3 実験パラメータ

| 実験                              | 目的                                | 変数               |
| --------------------------------- | ----------------------------------- | ------------------ |
| §3.1 cold vs warm baseline        | page fault コストの純粋な測定       | `--prefault`       |
| §3.2 アクセス局所性の影響         | Zipf α の変化による miss 率変化     | `--zipf-alpha`     |
| §3.3 MADV_WILLNEED 先読み         | page fault レイテンシを先読みで隠す | `--prefetch-ahead` |
| §3.4 マルチスレッド並行性         | page fault を並行 I/O で隠す        | `--threads`        |
| §3.5 Scan バッチプリフェッチ      | 複数ページを一括先読みしてから読む  | `--scan-width`     |
| §3.6 ホットセットサイズの影響     | mmap が勝つ境界条件の特定           | `--zipf-n`         |
| §3.7 Transparent Huge Pages (THP) | 2 MB 大ページによる TLB 削減効果    | `--huge-pages`     |

## 3. 実験結果

### 3.1 cold vs warm baseline（page fault コストの純粋な測定）

macOS と逆転した最大の結果：**cold でも mmap が LRU に勝つ**。

| 状態                                      | mmap (ops/sec) | pread+LRU (ops/sec) | LRU hit率 | 勝者          |
| ----------------------------------------- | -------------- | ------------------- | --------- | ------------- |
| **cold**（page cache クリア後）           | **18,545**     | 13,148              | 49.5%     | **mmap 1.4×** |
| **warm**（prefault で全ページロード済み） | **4,356,687**  | 13,251              | 49.5%     | **mmap 329×** |

**レイテンシ内訳（cold, α=1.0）:**

|     | mmap                                      | pread+LRU |
| --- | ----------------------------------------- | --------- |
| p50 | 0.24 µs ← **page cache hit（load 命令）** | 126.0 µs  |
| p95 | 166.4 µs ← **cold page fault**            | 165.9 µs  |
| p99 | 175.4 µs                                  | 177.4 µs  |

> **考察（なぜ cold mmap が LRU に勝つか）:**
>
> Zipf α=1.0、LRU hit 率 49.5% というデータが示すとおり、1M 回の操作のうち約 50 万回は LRU キャッシュにヒットし、残り 50 万回はミスする。
>
> - **LRU miss**: `pread + O_DIRECT` → 仮想ブロックデバイスで約 150 µs
> - **mmap fault**: page fault → カーネルトラップ + I/O → 約 166 µs（ほぼ同じ）
>
> 両者のミスコストはほぼ等しいため、**hit 時のコスト差**（mmap 0.24 µs < LRU ~1 µs 未満）が積み重なり、mmap が僅差で上回る。
>
> **warm mmap が 329× 速い**のは、`O_DIRECT` により LRU はページキャッシュの恩恵を受けられないため。warm 後も LRU の hit 率は 49.5% のまま変わらず、50% のミスが ~150 µs で頭打ちになる。

---

### 3.2 アクセス局所性の影響（Zipf α）

**macOS との最大の相違点**： macOS ではどの α の値でも LRU が勝つのに対し、**本環境では全 α 値で mmap が勝つ**。

| α（局所性）       | mmap (ops/sec) | pread+LRU (ops/sec) | LRU hit率 | 勝者                   |
| ----------------- | -------------- | ------------------- | --------- | ---------------------- |
| 0.5（ほぼ一様）   | 6,973          | 6,728               | **0.3%**  | **mmap 1.04×**（拮耶） |
| 1.0（標準 Zipf）  | 18,095         | 13,174              | 49.5%     | **mmap 1.37×**         |
| 1.5（局所性高）   | 501,487        | 435,153             | 98.6%     | **mmap 1.15×**         |
| 2.0（超局所集中） | 3,532,055      | 2,736,168           | **99.9%** | **mmap 1.29×**         |

**レイテンシ内訳（α=0.5）:**

|     | mmap     | pread+LRU |
| --- | -------- | --------- |
| p50 | 145.4 µs | 143.8 µs  |
| p95 | 169.3 µs | 167.0 µs  |
| p99 | 180.3 µs | 177.5 µs  |

> **考察:**
>
> **α=0.5（mmap 1.04×）:** LRU hit 率 0.3% でほぼ全アクセスが I/O に落ちる。mmap fault（~150 µs）と pread miss（~150 µs）が完全に均衡し、p50 がソックリ一致（145 µs vs 144 µs）。macOS（スループット比 83×）との極度の違いは「pread miss のコスト差」の実である。
>
> **α=1.0（mmap 1.37×）:** 50% が hit し、hit 時のコスト差（mmap 0.23 µs < LRU ~1 µs）が積み重なり mmap が勝越する。
>
> **α=1.5（mmap 1.15×）:** LRU hit 率 98.6% でありが、mmap はまだ勝つ。ただし p99=140 µs と穀な cold fault が残っており、両者の hit コスト（mmap 0.047 µs vs LRU 0.067 µs）は弥近しているため差が縮まる。
>
> **α=2.0（mmap 1.29×）:** LRU hit 率 99.9%、p99 mmap=0.12 µs と cold fault がほぼ消える。アクセスの大半が純粋な hit 勝負（mmap 0.045 µs vs LRU 0.065 µs）に帰着し、mmap が再び 1.29× に拡大する。
>
> **總論:** macOS では「pread miss が安いから LRU が常に勝つ」のの、Linux では「pread miss が要 page fault と同コストのため mmap が常に勝つ」。α をどれだけ大きくしても、ストレージの遅さが根本原因であるため mmap の優位は崩れない。

### 3.3 MADV_WILLNEED 先読みの効果

アクセスの N ステップ前に `madvise(MADV_WILLNEED)` を非同期発行し、page fault レイテンシを隠す。

| prefetch-ahead | mmap (ops/sec) | cold 比  | pread+LRU (ops/sec) | 勝者          |
| -------------- | -------------- | -------- | ------------------- | ------------- |
| 0（なし）      | 18,545         | 1×       | 13,148              | mmap 1.4×     |
| 8              | 66,477         | **3.6×** | 13,216              | **mmap 5.0×** |
| 32             | 185,217        | **10×**  | 13,223              | **mmap 14×**  |

**レイテンシ（prefetch-ahead=32）:**

|     | mmap                          | pread+LRU |
| --- | ----------------------------- | --------- |
| p50 | 0.25 µs                       | 129.2 µs  |
| p95 | 7.6 µs ← **先読みがほぼ成功** | 164.8 µs  |
| p99 | 35.3 µs                       | 174.6 µs  |

> **考察:** prefetch-ahead=32 で mmap が 14× に伸びる。LRU は `O_DIRECT` の制約により p50 が 129 µs のまま改善しないが、mmap は先読みで p95 を 166 µs → 7.6 µs に大幅削減できた。本環境では mmap の page fault コストと pread の I/O コストがほぼ等しいため、先読みで fault を隠した分だけ mmap が有利に転じる。

---

### 3.4 マルチスレッド並行性の効果

| threads | mmap (ops/sec) | cold 比  | pread+LRU (ops/sec) | LRU hit率 | 勝者          |
| ------- | -------------- | -------- | ------------------- | --------- | ------------- |
| 1       | 18,545         | 1×       | 13,148              | 49.5%     | mmap 1.4×     |
| 8       | 136,215        | **7.3×** | 81,034              | 36.5%\*   | **mmap 1.7×** |

\*LRU hit 率低下の理由: 各スレッドに独立 LRU（2,500 pages）を割り当てるため、実効バッファが分散する。

> **考察:** mmap はスレッド数 8× でスループットが 7.3× 改善（ほぼ線形）。仮想ブロックデバイスが並列 page fault を効率よく処理できていることを示す。LRU も 6.2× 改善しているが、各スレッドに独立 LRU を割り当てる設計上、hit 率が 49.5% → 36.5% に低下する。実際の KVS では共有 LRU を使うことが多く、その場合 LRU の hit 率低下は発生しない。

---

### 3.5 Scan バッチプリフェッチの効果（VMemKV §6.6 相当）

1 回の「スキャン操作」= N ページの `MADV_WILLNEED` を一括発行してから N ページを一括読み。

| scan-width | threads | mmap (ops/sec) | pread+LRU (ops/sec) | 勝者          |
| ---------- | ------- | -------------- | ------------------- | ------------- |
| 1（point） | 1       | 18,545         | 13,148              | mmap 1.4×     |
| 32         | 1       | 125,903        | 13,259              | **mmap 9.5×** |
| 32         | 8       | **328,866**    | 80,814              | **mmap 4.1×** |

> **考察:** scan-width=32 の単独スレッドで mmap が 9.5× に伸びる（threads=8 単独では 1.7×）。32 ページを一斉に MADV_WILLNEED することで OS が I/O を最適化・並列化できるためと考えられる。threads=8 + scan-width=32 の組み合わせでは mmap 328K ops/sec に到達する。

### 3.6 ホットセットサイズの影響

`--zipf-n` でホットキー空間を変化させ、hot set が大きくなるにつれてどう性能が変わるかを測定する。

| zipf-n（hot 空間） | hot set サイズ              | mmap (ops/sec) | pread+LRU (ops/sec) | LRU hit率 | 勝者          |
| ------------------ | --------------------------- | -------------- | ------------------- | --------- | ------------- |
| 20,000             | **80 MB**（LRU と同サイズ） | **563,651**    | 293,836             | 98.0%     | **mmap 1.9×** |
| 200,000            | **800 MB**（LRU の 10×）    | **60,739**     | 25,996              | 74.6%     | **mmap 2.3×** |
| 2,000,000          | **8 GB**（LRU の 100×）     | **26,885**     | 16,613              | 60.1%     | **mmap 1.6×** |
| 25,165,824         | **96 GB**（全体）           | 18,545         | 13,148              | 49.5%     | mmap 1.4×     |

> **考察:** hot set が小さくなるほど mmap の優位性が増す。hot set = 80 MB（LRU バッファと同サイズ）でも mmap が 1.9× 速い。これは LRU hit 率が 98% に達しても、mmap の page cache hit（~0.07 µs）が LRU hit よりも速いためである。hot set が大きくなるにつれて cold fault が増加し性能がほぼ単調に低下するが、全サイズで mmap が LRU を上回る（LRU の O_DIRECT ミスコスト ~150 µs が大きく効いている）。

### 3.7 Transparent Huge Pages (THP) の効果（Linux 専用実験）

`--huge-pages` を指定すると `madvise(MADV_HUGEPAGE)` により OS が 4 KB ページを 2 MB 大ページに昇格する。

| 実験                 | THP  | mmap (ops/sec) | pread+LRU (ops/sec) | mmap p99     | 勝者          |
| -------------------- | ---- | -------------- | ------------------- | ------------ | ------------- |
| warm                 | なし | 4,356,687      | 13,251              | 0.70 µs      | mmap 329×     |
| warm + THP           | あり | **2,509**      | 13,211              | **2,788 µs** | LRU **5.3×**  |
| cold                 | なし | 18,545         | 13,148              | 175 µs       | mmap 1.4×     |
| cold + THP           | あり | **2,558**      | 13,210              | **2,764 µs** | LRU **5.2×**  |
| hot set 80 MB        | なし | 563,651        | 293,836             | 140 µs       | mmap 1.9×     |
| hot set 80 MB + THP  | あり | **7,408,076**  | 294,724             | **0.22 µs**  | **mmap 25×**  |
| hot set 800 MB       | なし | 60,739         | 25,996              | 168 µs       | mmap 2.3×     |
| hot set 800 MB + THP | あり | **5,174,393**  | 26,057              | **0.65 µs**  | **mmap 199×** |

**THP が与える二種類の効果：**

#### ① ホットセットが小さい場合：劇的な高速化

- 80 MB hot set = 20,000 × 4 KB = **40 × 2 MB 大ページ**に圧縮される
- L2 TLB（Xeon Gold 6138: ~1,024 エントリ）に 40 エントリで完全に収まる
- ページテーブルウォークが消え、全アクセスが DRAM 直接アクセスに
- 結果: mmap **7.4M ops/sec（25× 改善、p99 = 0.22 µs）**

#### ② ホットセットが大きい場合（warm / cold 全データセット）：壊滅的な低下

- 96 GB × 4 KB ページ を 2 MB に昇格するには memorycompaction（大量の連続物理フレーム確保）が必要
- 本環境の 16 GB RAM では 96 GB ファイルのページを常に昇格しようとする khugepaged が大量の compaction stall を引き起こす
- p95 = **2,578 µs、p99 = 2,764 µs**（compaction I/O ストール）
- 結果: warm にもかかわらず mmap **2,509 ops/sec（1,736× 劣化）**

> **考察:** THP の効果は hot set サイズと RAM 容量の比によって正反対に働く。
>
> - `hot set ≪ RAM`（例: 80 MB hot set / 16 GB RAM）→ THP 昇格が容易、TLB エントリが激減 → **大幅な高速化**
> - `hot set ≈ RAM` または `hot set ≫ RAM` → compaction が常時発生 → **壊滅的な低下**
>
> したがって THP は VMemKV の適用場面（ホットデータが RAM に収まるワークロード）において本来非常に有利な条件が整いやすい。ただし THP の設定は `madvise`（アプリが明示的に要求した場合のみ昇格）に留め、`always`（OS が全域で積極昇格）は避けるべきである。

## 5. 考察

### 5.1 本環境でのアクセスコスト構造

```
本環境のレイテンシ（実測値）:
  mmap — page fault:     ~166 µs（KVM 仮想ブロックデバイス経由のカーネルトラップ）
  pread + O_DIRECT:      ~150 µs（同 I/O パス、ほぼ同コスト）
  mmap — page cache hit: ~0.2 µs（load 命令のみ）
  LRU cache hit:         < 1 µs（ハッシュ引き + リスト操作）
```

mmap の fault コストと pread の I/O コストがほぼ等しいため、**hit 時のコスト差（mmap 0.2 µs < LRU ~1 µs）** が性能を決定する。Zipf 分布により 49.5% の操作が hit するため、mmap の hit 優位が積み重なり全体スループットで mmap が上回る。

### 5.2 cold mmap が LRU を超えるメカニズム

```
1M 操作（hit 率 49.5%）のシンプルなモデル:

LRU:
  total_time = 495,000 × t_hit + 505,000 × t_miss
             ≈ 495,000 × 0.001ms + 505,000 × 0.150ms
             ≈ 0.5s     +    75.8s    = 76.3s
  throughput ≈ 13,100 ops/sec ✓

mmap:
  total_time = 495,000 × t_hit + 505,000 × t_fault
             ≈ 495,000 × 0.0002ms + 505,000 × 0.166ms
             ≈ 0.1s     +    83.8s    = 83.9s
  throughput ≈ ??  ... 手計算上は LRU より遅い?
```

実測では mmap 18,545 > LRU 13,148 であり、モデルより mmap が速い。これは fault 中も残りのページが page cache にある限り並列に処理されるカーネルの非同期性や、仮想化環境でのスレッドスケジューリングの影響が考えられる。

### 5.3 THP の効果 — two-regime behavior

```
Regime A: hot set ≪ RAM （small hot set）
  → THP で 4KB → 2MB に昇格
  → TLB エントリ数: n_pages → n_pages / 512
  → 80 MB hot set: 20,000 TLB エントリ → 40 TLB エントリ
  → TLB miss 消失 → 純 DRAM 帯域で動作
  → mmap 25–199× 速くなる ✓

Regime B: hot set ≈ RAM 以上（large hot set）
  → khugepaged が全ペ ージを 2MB に昇格しようと compaction を実行
  → RAM 16GB に対し 96GB ファイルの compaction は物理不可能
  → 定常的に compaction stall → p95 が 2,600 µs に
  → throughput 2,500 ops/sec まで崩壊 ✗
```

### 5.4 VMemKV 設計への示唆

| 設計判断                                                   | 本実験での根拠                                                                 |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------ |
| **ホットデータを RAM に収めるアーキテクチャ前提**          | Regime A（hot set ≪ RAM）でのみ THP + mmap が圧倒的に有利                      |
| **THP は `madvise` モードで使用すること**                  | `always` モードでは大きな working set で compaction stall が致命的（Regime B） |
| **`--huge-pages` は hot set サイズを事前に見積もって使用** | hot set が RAM に収まる確信がある場合のみ有効化する                            |
| **warm + 小 hot set は最も VMemKV が輝く条件**            | hot set 800 MB + THP で **mmap 199×**、VMemKV の設計根拠として最も強い証拠    |

| warm で mmap は LRU より速いか？        | **はい**（mmap 329×）                    |
| cold + α=0.5（一様分布）では？          | **同等**（1.0×）                         |
| MADV_WILLNEED で cold を補えるか？      | **十分**（mmap が LRU を 14× 上回る）    |
| hot set が LRU バッファに収まる場合は？ | **はい**（mmap 1.9×）                    |
| THP（small hot set）の効果は？          | **絶大**（mmap **25×**、199×）           |
| THP（全 working set）の効果は？         | **壊滅的**（mmap 0.19×）                 |
| VMemKV が最も有利な条件は？            | hot set が RAM < 1/6、THP madvise モード |

> **総括:** 本環境（Linux KVM + 仮想ブロックデバイス）では、mmap の page fault コスト（~166 µs）と pread + O_DIRECT の I/O コスト（~150 µs）がほぼ等しい。このコスト均等化により cold 条件でも mmap が LRU を上回った。さらに THP を適切に（hot set を RAM に収める条件で）使用すると mmap が pread+LRU の 25–199× に達し、VMemKV の設計根拠を強く支持する結果となった。
