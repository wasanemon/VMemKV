# 2026-08-06 Scan性能とT2 madvise(MADV_RANDOM)の関係についての考察

## 背景

`20260805_ltm_get_hit_profiling.md` の追記で修正されたベンチマーク手法(RocksDB-BlobDBのページキャッシュ共有アーティファクト排除、`drop_caches`の対称化)を反映した2026080600実験(`benchmark_results/pages/2026080600_charts.html`)でも、VMemKVは依然として **Scan系ワークロードで一貫して劣後**していた(Summary表の "Scan (T1 Reorg)" / "Scan (T1+T2 Reorg)" 行は8B/1KB In-Memoryではほぼ互角〜わずかに負け、LTM(1KB/64KB)では 0.07x〜0.47x とRocksDB/LMDBに大きく負けている)。

本ドキュメントは、この根本原因が **`T1_index` ではなく `T2`(value store)側の `madvise(MADV_RANDOM)`** に起因すること、そしてこの最適化が単純な「有効/無効」の二択ではなく、**アクセスパターン(Get=random vs Scan=sequential)と物理レイアウト(T2がreorganize直後でソート済みかどうか)の両方に依存するトレードオフである**ことをAWSスポットインスタンスでの実測に基づいてまとめる。

結論を先に述べる:

1. **実装バグにより、`NoMadvise` アブレーションはScanベンチマークに対して事実上無効化されていた**。`mmap_t2_memory()`(reorganize/checkpoint後のT2再mmap経路)が `ConfigT::UseMadviseRandom` を無視して常に `MADV_RANDOM` を適用しており、"reorg後" を計測するあらゆるScanベンチマークが、`NoMadvise` 指定でも実際にはBaseline同様 `MADV_RANDOM` 下で計測されていた。これを修正した(commit `1c659e1`)。
2. **修正後の実測により、`MADV_RANDOM` はGetを2〜4.3倍速くする一方でScanを1.7〜2.3倍遅くする、真のトレードオフであることを確認した**。低レベル設計書(7.7節)が記す「in-memory Get_Hitで約5%改善」は正しいが、LTM(スワップが実際に発生する環境)ではその効果はずっと大きく、Scan側の悪化も同程度に大きい。
3. **この効果は「Scanかどうか」だけでなく「T2が物理的にソート済みかどうか」に完全に依存する**。T1-onlyのreorganize直後(T2は未整理のまま)ではmadviseの有無はScan性能に**測定誤差レベルの影響しか与えない**。T2が完全reorganize(checkpoint)直後でキー順に並んでいるときだけ、madviseの選択が2倍前後効いてくる。
4. **方針として、T2の `madvise` は常時 `MADV_RANDOM`(現状維持)とし、Scanの改善は別のレバー(アプリケーション側の並列プリフェッチ)で狙う。** Scan単位でmadviseを動的に切り替える設計(結果2の考察で挙げた「ソート済み境界オフセット」案)は、advise/revertペアの実装・世代スワップとの整合性・呼び出し頻度など相応の実装コストがあり、かつ「GetはScanよりはるかに呼び出し頻度が高い」という非対称性のため、同種の仕組みをGet側に入れる発想(結果1のトレードオフを逆手に取る案)はさらに分が悪い。代わりに、独立したマイクロベンチマークで「madviseを一切使わず、複数スレッドで並行してページタッチするだけでI/O待ちが重なるか」を検証したところ、8コアで約7.15〜7.16倍という、ほぼ線形のスループットスケーリングを確認した(結果3)。これはmadvise設定に一切手を入れずにScanを改善できる可能性を示しており、Get側の実績あるmadvise設定を壊すリスクを取らずに済む。
5. **しかし、結果3〜6の有望なマイクロベンチマーク結果を踏まえてio_uringベースの並列プリフェッチを`scan_impl`に実装・実システムで検証したところ、Baselineより3〜6倍遅いという結果になり、不採用として差し戻した(結果7)。** 並行発行(既定チャンク数)は極端に逼迫したLTM環境下で数分間のハングを引き起こし、直列化(chunk=1)でハングは解消したがそれでも大幅に遅い。マイクロベンチマークと実システムの結果がここまで乖離した理由(作業単位のサイズの違いは一部説明するが、大部分は未特定)を含め、結果7に詳細を記録している。
6. **結果7後に「実装バグの可能性」を切り分けるため再検証したところ、実装バグではなく2つの具体的なメカニズムで説明がついた(結果8)。** タイミング計装により、chunk=1の遅さはバッチ化ゼロのsyscallオーバーヘッドで完全に説明できることを確認。適正なchunk数(32)に戻すと実システムでもBaseline並みまで戻るが、それでも上回れない理由をmajor fault計測で直接確認したところ、極端なオーバーサブスクリプション(8倍)下で「プリフェッチしたページが実際の読み取り前に再度追い出される」競合状態が起きていることが分かった。**この追加検証でも「Scanを速くする有効な手立て」は見つからず、結論(madvise常時RANDOM維持、io_uringプリフェッチは不採用)は変わらないが、根拠は未特定の複合要因から具体的で理解可能なメカニズムに置き換わった。**

以下、詳細を述べる。

## 発見の経緯: `NoMadvise` アブレーションが機能していなかった

`implementation/src/vmemkv_impl.hpp` を確認すると、`madvise()` の呼び出しは2箇所にしか存在しない。

1. コンストラクタ内、初回のT2 mmap時(187-192行目)。ここは `if constexpr (ConfigT::UseMadviseRandom)` で正しくガードされている。
2. `mmap_t2_memory()`(959-981行目)。reorganize/checkpoint reload でT2を作り直すたびに呼ばれる、共有の再mmapヘルパー。**修正前はここに `if constexpr` ガードが無く、`ConfigT::UseMadviseRandom` の値に関わらず常に `MADV_RANDOM` を適用していた。**

`Scan_WithReorg` / `Scan_T1T2Reorg` を含め、"reorg後" の状態を計測するベンチマークは必ずこの2番目の経路を通ってT2が構築される。したがって `NoMadvise` バリアントを指定していても、Scanベンチマークで計測される実際のT2マッピングには常に `MADV_RANDOM` がかかっていた ―― `2026080600_charts.html` で `NoMadvise` のScan系数値が `Baseline` とほぼ完全に一致していたのはこのためであり、そもそもこのアブレーションはScanに関して何も検証できていなかったことになる。

修正(commit `1c659e1`)は `mmap_t2_memory()` の `madvise()` 呼び出しを `if constexpr (ConfigT::UseMadviseRandom)` でガードするだけの2行差分。

## 環境・手法

- インスタンス: AWS `i4i.2xlarge`(ap-northeast-1a)、スポット、8 vCPU、ローカルNVMe。`run_bench_aws_c6id.sh` が使う `i4i.8xlarge` よりコアを絞り、1イテレーションを10分以内に収める前提で選定。
- LTM cgroup: `systemd-run -p MemoryHigh=1GiB -p MemoryMax=2GiB -p MemorySwapMax=1TiB`(本番ベンチマークと同一設定)。`VMEMKV_BENCH_TARGET_RATIO=8.0` により8倍オーバーサブスクリプション、1KB値で8,259,552キー。
- **`VMEMKV_CONTEXT_memory_budget_bytes` はcgroup外の「プライミングパス」でも明示的に指定する必要がある**: `bench_kv` の `detect_machine_memory_bytes()` はこの環境変数が無いとcgroup limit → `/proc/meminfo` の順にフォールバックするため、指定を忘れるとプライミングパスがホスト全体のRAM(数十GB)を基準に8倍のコーパスを構築しようとして事実上ハングする。
- コーパス構築: cgroup外の「プライミングパス」で共有マスターコーパスを一度構築してから、cgroup制約下の計測プロセスがそこから高速にクローンする(本番ベンチマークと同一設計、`VMEMKV_BENCH_SKIP_CLEANUP=1` でクローン元を保護)。cgroup内でゼロから8倍オーバーサブスクリプションのコーパスを構築すると200〜1200秒かかるが、プライミングは無制約なので20〜30秒で済む。
- 計測直前に `sync && echo 3 | sudo tee /proc/sys/vm/drop_caches` でページキャッシュを破棄し、`20260805_ltm_get_hit_profiling.md` で確認済みのページキャッシュ共有アーティファクトを避けている。
- ビルド: `-O3 -DNDEBUG -march=native`、`--benchmark_min_time=3s`。
- 比較対象は VMemKV の `Baseline`(`MADV_RANDOM` 常時有効)と `NoMadvise`(本ドキュメントの修正適用後、T2に一切madviseしない)の2バリアントのみ。RocksDB/LMDBとの比較は行わず、VMemKV内部の要因分析に絞った。

## 結果1: `MADV_RANDOM` はGetとScanで正反対に効く

1KB値、1スレッド、LTM cgroup下での比較(`Scan_T1T2Reorg` = T1+T2完全reorganize直後、T2はキー順にソート済み):

| ワークロード | Baseline (MADV_RANDOM) | NoMadvise | 比率 |
|---|---:|---:|---:|
| Scan (T1+T2 Reorg), Zipf | 2,214 items/s | 5,108 items/s | NoMadvise **2.31倍**速い |
| Scan (T1+T2 Reorg), Uniform | 777 items/s | 1,332 items/s | NoMadvise **1.71倍**速い |
| Get (Hit), Zipf | 19,829 items/s | 9,533 items/s | Baseline **2.08倍**速い |
| Get (Hit), Uniform | 10,292 items/s | 2,408 items/s | Baseline **4.27倍**速い |

低レベル設計書7.7節は「madviseの適用によって in-memory Get_Hit において約5%の有意な性能向上効果」と記しているが、これはページキャッシュに乗っている(スワップが発生しない)環境での効果であり、**実際にスワップI/Oが発生するLTM環境での効果はその数十倍(2〜4.3倍)に達する**。理由は明確で、`MADV_RANDOM` はカーネルのreadahead(先読み)を抑止するヒントであり、真にランダムなアクセスパターンでは「次にアクセスしないページ」を先読みして貴重なスワップI/O帯域を浪費するのを防ぐ。逆にsequentialなアクセスパターン(reorganize後にキー順で並んだT2を範囲走査するScan)では、この抑止がそのまま「本来なら1回のI/Oでまとめて読めたはずのページ群を、1ページずつ個別にフォールトさせる」という逆効果になる。

madviseは「有効にすれば安全に速くなる最適化」ではなく、**アクセスパターンに応じて損得が完全に反転するトレードオフ**である。

## 結果2: 効果は「T2が物理的にソート済みかどうか」に完全に依存する

`Reorganizing Two-Region` 構造(high_level_design.md 3節)では、T2がキー順に整列するのは **T2 reorganize(checkpoint)完了直後だけ**である。それ以降のinsert/out-of-place updateは常にT2の末尾に到着順で追記され(high_level_design.md 4.2節)、T1-onlyのreorganizeはT2に一切触れない(low_level_design.md 4.2節)。つまり2回のT2 reorganizeの間、T2は「reorg時点でキー順に整列済みのbase領域」+「その後の追記による到着順のtail領域」という構造になる。

この違いが実際にmadviseの効果を左右するかを検証するため、同一のLTM cgroup条件で `Scan_WithReorg`(T1-onlyのreorganize直後、T2は未整理=到着順のまま)と `Scan_T1T2Reorg`(T1+T2完全reorganize直後、T2はキー順)を比較した:

| モード | 分布 | Baseline | NoMadvise | 比率 |
|---|---|---:|---:|---:|
| T1-only reorg(T2未整理) | Zipf | 176.69 items/s | 176.04 items/s | **0.996x(実質差なし)** |
| T1-only reorg(T2未整理) | Uniform | 105.26 items/s | 105.23 items/s | **1.00x(実質差なし)** |
| T1+T2 reorg(T2ソート済み) | Zipf | 2,285 items/s | 5,257 items/s | NoMadvise **2.30倍**速い |
| T1+T2 reorg(T2ソート済み) | Uniform | 703 items/s | 1,343 items/s | NoMadvise **1.91倍**速い |

T2が未整理の状態では、Baseline/NoMadviseの差は誤差の範囲(1%未満)に収まる。到着順に散らばったデータには活かせる物理的局所性がそもそも存在しないため、readaheadを許しても妨げても結果は変わらない。T2がソート済みの状態でだけ、madviseの選択が2倍前後という大きな差を生む。

この結果は、結果1で見た「Baseline/NoMadviseどちらが良いか」という問いが、実は**Scanかどうかだけでなく、対象データが物理的に整列しているかどうかにも依存する二軸の問題**であることを示している。

## 考察: なぜ単純な「Get用/Scan用の使い分け」では不十分か

Scanの間だけ `MADV_RANDOM` を外す、という素朴な設計(例えば低レベル設計書4.5節で既に実装されている `scan_active_` フラグに相乗りする)には、次の2つの技術的な制約がある。

1. **madviseはメモリマッピング全体に対するヒントであり、呼び出し単位で切り替えられない。** 同一のT2マッピングに対してGetとScanが並行して走っている(混在ワークロード)場合、「このGet呼び出しだけRANDOM、この並行するScan呼び出しだけSEQUENTIAL」という制御はできない。Scanのために `MADV_RANDOM` を外せば、その期間中に並行するGetも巻き添えでreadaheadの恩恵(というより浪費防止)を失う。
2. **`scan_active_` は実際には「直近のreorganizeの後、一度でもScanが呼ばれたか」を示すsticky(粘着的)なフラグ**であり(`vmemkv_impl.hpp` 830-832行目でセット、483行目でreorganize完了時にのみクリア)、個々のScan呼び出しの開始・終了とは対応していない。読み込み主体でreorganizeが滅多に起きないワークロードでは、一度でもScanが走ると長時間 `true` のまま張り付き、その間ずっと並行するGetが不利益を被り続ける可能性がある。

しかし、結果2の知見はこの設計空間を大きく単純化する。**T2が未整理の状態ではmadviseの選択が無害(どちらでも同じ)なので、Get+Scan混在への巻き添えを心配すべき局面は「T2がソート済みのときにScanが発生した場合」だけに絞られる。** 逆に言えば、T2が未整理の間はmadviseの切り替えについて何も考える必要がない。

具体的な実装方針としては、各T2世代について「直前のT2 reorganize完了時点の `bytes_used`」(`commit_checkpoint()` に渡している `next_bytes_used` として既に値自体は存在する)を「ソート済み境界オフセット」として保持し、

- offset < 境界: base領域、キー順に整列済み → sequentialなヒントが正しく効く対象
- offset >= 境界: tail領域、到着順で事実上ランダム → 結果2よりmadviseの選択に意味が無いので `MADV_RANDOM` のままでよい

という判定を導入することで、Scanの候補offset集合がbase領域に属するかどうかに応じてヒントを出し分けられる可能性がある。これは今回のドキュメントでは設計の方向性としてのみ記録し、実装・検証は別途行う。

さらに、この設計を裏から見ると **Get側でmadviseを都度切り替える(デフォルトsequential、Get呼び出し時だけRANDOMを指示する)という逆方向の案も同じ実装コストで実現できる**が、これは得策ではない。VMemKVの実測(Get_Hitは1スレッドで1万〜2万 items/s、Scanは1回で100件をまとめて処理するため呼び出し回数はずっと少ない)を踏まえると、advise/revertペアのシステムコールをGet側に入れると、Scan側に入れる場合よりも遥かに高頻度で払うことになる。これは7.4.1節で不採用になった「Get毎の`MADV_WILLNEED`」(呼び出し頻度の高さが原因で1.28〜6.4倍悪化)と同じ失敗パターンを踏む可能性が高く、採用しない。

## 結果3: madviseを使わずアプリ側で並列プリフェッチしても、I/O待ちはほぼ線形に重なる

結果1・結果2を踏まえ、「T2のmadviseは常時 `MADV_RANDOM`(Get保護を優先)のまま固定し、Scanは別の手段で改善する」という方針を検討した。有力な候補は、**`madvise`を一切使わず、複数スレッドで並行してT2の生ページタッチを行い、swap/page cache evictionによるI/O待ちを重ねる**というアプリケーション側の並列プリフェッチである。

この核心メカニズム(「madviseを介さない、複数スレッドの並行タッチだけでI/O待ちが重なるか」)を、VMemKVの実装に触れず独立したマイクロベンチマーク(`implementation/microbenchmark/bench.cpp`、既存のmmap vs pread+LRU比較ツール)の `--threads` オプションを使って検証した。この経路は `madvise(m, total, MADV_RANDOM)` を固定で適用しているので(`bench.cpp` 279行目)、「T2をmadvise常時RANDOMのまま」という決定した方針とも整合する条件になっている。

**手法**: AWS `i4i.2xlarge`(8 vCPU)、`systemd-run -p MemoryHigh=1GiB -p MemoryMax=2GiB` のcgroup下、8GBのデータファイル(`MAP_SHARED`読み取り専用、4KBページ)に対し、point mode(1回のアクセスにつき1ページを読むだけの単純なランダム/Zipfアクセス、prefetchやscan-widthは無効)で、threads=1とthreads=8のスループットを比較した。`--ops` は全スレッド合計で固定(20,000)なので、スレッド数を増やしても総仕事量は変わらず、純粋に並行実行によるI/O待ちの重なりだけを見ている。計測直前に `drop_caches` でページキャッシュを破棄している。

| 分布 | threads=1 | threads=8 | スケーリング |
|---|---:|---:|---:|
| Zipf α=1.0 | 15,395 ops/s | 110,156 ops/s | **7.16倍**(理論上限8倍中) |
| Uniform相当(α=0.0001) | 7,570 ops/s | 54,096 ops/s | **7.15倍**(理論上限8倍中) |

8コアに対してほぼ線形(7.15〜7.16倍)のスループットスケーリングが得られた。これは、`20260805_ltm_get_hit_profiling.md` で確認済みの「VMemKVのボトルネックはmmap_lock競合ではなく純粋なブロックI/O待ち」という知見と整合する: mmap_lock自体が詰まっていないなら、複数スレッドが独立にI/O待ちすることで、その待ち時間を重ねられるはずである。旧 low_level_design.md 7.4.1節(現在は削除。結果4参照)は `MADV_WILLNEED` の悪化原因を「madvise呼び出し自体がmmap_lockを奪い合った」ためと推定していたが、この推定は直接検証されておらず、後日(結果4)直接計測した結果、誤りだったことが分かった。今回の実験は一切madviseを呼ばず生のページタッチのみを行っている点は変わらない。

### 結論

Scan性能の改善は、T2のmadvise設定(常時`MADV_RANDOM`、Get保護のため現状維持)に手を入れずに、**アプリケーション側で複数スレッドを使った並行プリフェッチを`scan_impl`に組み込む**方向で狙うのが筋が良いと判断する。ただしこれは単純化されたマイクロベンチマークでの検証であり、実際の`scan_impl`への組み込みでは次の点を別途検討する必要がある。

- 1回のScan呼び出しのためだけに新しいスレッドを立てるコストは高いため、既存のスレッドプールや、ベンチマーク環境で既に動いている並行スレッド(32スレッド等)をどう活用するかの設計が必要。
- T1-onlyのreorganize直後(結果2の「T2未整理」状態)では、そもそも物理的な局所性がない(candidate offsetが散らばっている)ため、並列プリフェッチしても各タッチ自体は独立したI/O待ちのままである。並列化の恩恵(重なる待ち時間)は得られる可能性があるが、これは結果2の「sortedかどうか」の議論とは独立の効果である点に注意。
- 実際のT2(`MAP_PRIVATE`、COWで書き込みが加わる)は、本実験の`MAP_SHARED`読み取り専用ファイルとは異なり、スワップ(anonymous pages)を伴う。ページキャッシュのevict+re-readとスワップのpageout/pageinとで、並行タッチのスケーリング特性が完全に同じとは限らないため、`vmemkv_impl.hpp`側での再検証が必要。

## 結果4: `mmap_lock`は直接計測すると詰まっていない — 旧7.4.1節の原因推定を訂正

結果3を受けて、「スレッドを使わずに、`io_uring`等で非同期にmadviseを一律発行できないか」を検討する過程で、旧 low_level_design.md 7.4.1節(`MADV_WILLNEED` 不採用の節、本ドキュメントの更新に伴い削除済み)の「原因はmmap_lock競合」という推定を疑い直した。7.4.1節はこの推定を実際にはロック自体を計測せずに述べていた(単一スレッドでの悪化は、そもそも競合相手がいないので理屈上ロック競合では説明できない)。この推定を検証せずに設計判断の根拠にしていたのは適切でなかったため、直接計測した。

**手法**: 同じマイクロベンチマーク(`bench.cpp`)の `--prefetch-ahead 1` オプション(1手先のアイテムに対して `madvise(MADV_WILLNEED)` を発行してから現在のアイテムをタッチする、1スレッド内のソフトウェアパイプライン)を使用。AWS `i4i.2xlarge`、1GiB cgroup、8GBデータセット、Zipf α=1.0。まずスループットを素のタッチ(結果3と同条件)と比較し、次に `perf record -e mmap_lock:mmap_lock_start_locking,mmap_lock:mmap_lock_acquire_returned` でロック取得のたびの開始/完了イベントを記録し、スレッドごとに直近の `start_locking` と次の `acquire_returned` のタイムスタンプ差分を取ってロック取得レイテンシの分布を求めた(カーネル6.17、`mmap_lock` トレースポイントが利用可能)。

**スループット比較**(threads=1 と threads=8):

| モード | threads=1 | threads=8 | 倍率(1→8) |
|---|---:|---:|---:|
| 素のタッチ(madvise無し) | 15,244 ops/s | 109,903 ops/s | 7.21倍 |
| `--prefetch-ahead 1`(都度madvise) | 21,918 ops/s | 111,368 ops/s | 5.08倍 |

1スレッドでは prefetch-ahead が素のタッチより **1.44倍速い**(21,918 vs 15,244)。ところが8スレッドでは両者がほぼ同じ絶対値(111,368 vs 109,903)に収束し、prefetch-aheadの1スレッド時の優位がほぼ消える。

**`mmap_lock` 取得レイテンシの直接計測**(8スレッド、`--prefetch-ahead 1`実行中、51,449サンプル):

| 指標 | 値 |
|---|---:|
| 平均 | 0.37 μs |
| p50 | 0 μs |
| p95 | 1 μs |
| p99 | 1 μs |
| p99.9 | 8 μs |
| 最大 | 24 μs |

タッチ1回のコスト(約50〜65μs)に対して、ロック取得自体のコストは無視できる水準であり、**8スレッド並行・都度madvise呼び出しという条件下でも`mmap_lock`は詰まっていない**ことを直接確認した。

### 結論

- 旧7.4.1節の「原因はmmap_lock競合」という推定は、少なくとも同種の呼び出しパターン(1手先読みのソフトウェアパイプライン)・この並行度(8スレッド)では支持されない。7.4.1節はこの実験結果ごと削除し、本ドキュメントに検証つきで記録し直した。
- 8スレッドでprefetch-aheadの優位が消えた理由はロック競合ではなく、より単純に「8スレッドの並行生タッチだけで既にI/O待ちの重ね合わせがほぼ飽和しており、そこにmadviseを足す伸びしろが無い(かつmadvise自体のCPU/syscallコストが純増する)」ためと考えられる(直接の原因特定は未検証、推測)。
- **1スレッドでの`madvise(MADV_WILLNEED)`一手先読みパイプラインは、追加スレッドを一切使わずに1.44倍の改善になる**。これは結果3の「複数スレッドでの並行生タッチ」(最大約7倍、ただしスレッドプールの設計コストとオーバーサブスクリプションのリスクを伴う)とは独立した、実装コストの低い選択肢として使える。並行呼び出し元が既に多く追加スレッドを避けたい局面では、この1スレッド版パイプラインへのフォールバックが有力な候補になる。

## 結果5: io_uringで分割発行すれば、自前スレッドプール無しで並行生タッチ相当の性能が出る

結果4を受け、「`mmap_lock`が詰まらないなら、`io_uring`で`madvise`系操作を非同期一律発行すれば、スレッド作成コストを払わずに並行I/O待ちの重ね合わせを得られるのでは」という案を検証した。当初 `MADV_POPULATE_READ`(Linux 5.14〜、範囲を確実にフォールトさせる強い保証を持つ、`WILLNEED`より用途に適した先読みフラグ)を素朴に使う案が浮上したが、これはブロッキングな呼び出しであり、単体では並行性を生まないことが分かったため(後述)、`io_uring`と組み合わせる方向で検証した。

**手法**: 専用のマイクロプローブ(`liburing`使用、VMemKVには非依存)を新規に書き、Scanの1バッチに相当する「連続した100ページの窓」を200個(各回とも独立の乱数選択、他手法とウィンドウが重複しないようシード分離)処理する所要時間を、4手法で比較した。AWS `i4i.2xlarge`、1GiB `MemoryHigh` cgroup、8GBデータセット(`MAP_SHARED`読み取り専用、結果3と同条件)。

- **生タッチ 1スレッド**: 100ページを順にタッチするforループ。
- **生タッチ 8スレッド**: 100ページを8等分し、`std::thread`8本で並行タッチ(結果3の点アクセス版と同じ考え方を、連続窓に適用したもの)。
- **`MADV_POPULATE_READ` 一括(1スレッド)**: 100ページ全体に対して`madvise(MADV_POPULATE_READ)`を1回呼んでからタッチ。
- **io_uring(8分割SQE)**: 100ページを8等分し、チャンクごとに`io_uring_prep_madvise(..., MADV_POPULATE_READ)`のSQEを作成、`io_uring_submit()`で一括投入してから全チャンクの完了を待つ。呼び出し元スレッドは1本のみ(追加の`std::thread`は一切生成しない)。

**初回の実験設計ミス**: 最初は100ページの窓全体を1つのSQEにまとめて投入していた。この構成では並行性が生まれる余地が無く、生タッチ1スレッド・`MADV_POPULATE_READ`一括と誤差レベルで同じ結果になった(mean 13,029.3us vs 13,468.5us/13,317.9us)。io_uringの強みは「投げっぱなしで戻れる」ことではなく「複数の作業を同時に投げられる」ことなので、複数SQEに分割しない限り並行化されない。分割版に修正して再計測した。

**結果**(分割後、100ページ窓、200バッチ):

| 手法 | 平均レイテンシ | スループット | 倍率(対1スレッド) |
|---|---:|---:|---:|
| 生タッチ 1スレッド | 11,509.0 μs | 86.9 windows/s | 1.00倍 |
| 生タッチ 8スレッド | 1,976.0 μs | 506.1 windows/s | **5.82倍** |
| `MADV_POPULATE_READ` 一括(1スレッド) | 11,404.0 μs | 87.7 windows/s | 0.99倍(誤差) |
| io_uring(8分割SQE、呼び出しスレッドは1本) | 1,961.4 μs | 509.9 windows/s | **5.82倍** |

### 結論

- `MADV_POPULATE_READ`を範囲一括で1回呼ぶだけでは、内部的な先読みバッチ化のような恩恵は無く、生タッチのforループと文字通り同じ速度だった。この操作はブロッキングであり、単体では並行性を生まない。
- **io_uringで窓を複数チャンクに分割してSQEを一括投入すれば、`std::thread`を1本も自前で作らずに、8スレッドの生タッチとほぼ完全に同じ性能(509.9 vs 506.1 windows/s)が得られた。** カーネルの`io-wq`ワーカープールが並行I/O待ちの重ね合わせを肩代わりしており、アプリ側のスレッドプール設計・オーバーサブスクリプション管理をせずに済む。
- これは、結果3で洗い出した「スレッドプールのサイズ設計」「呼び出し元スレッド数とのオーバーサブスクリプション」といった課題を、`io_uring`のSQE分割数(チャンク数)というパラメータに置き換えられる可能性を示している。チャンク数は`io-wq`のワーカー数上限に従うため、際限なくOSスレッドが増える心配が少ない(要検証)。
- ただしこれは`MAP_SHARED`読み取り専用ファイルでの代理実験であり、実際のT2(`MAP_PRIVATE`・COW・スワップ)での再検証、および`scan_impl`への組み込み設計はまだ行っていない。

## 結果6: チャンク数(SQE分割数)8はコア数に合わせただけの数字で、最適ではない

結果5では、生タッチのスレッド数(コア数=8)に合わせてio_uringのSQE分割数も8にしていた。しかしio_uringはOSスレッドを自前で作らないため、分割数をコア数に縛る理由は無い。NVMeは本来もっと高い並行I/Oを裁けるハードウェアであり、ユーザランドの同期的な1操作ずつのブロッキングが並行性を殺しているだけなのだとすれば、分割数を増やすほど(ある上限までは)スループットが伸びる可能性がある。

**手法**: 結果5のプローブに `--chunks`(SQE分割数、`--threads`とは独立)と `--seed-offset`(呼び出しごとに異なる乱数窓を使う。**最初の試行では複数回の実行が同じ200窓を使い回してしまい、2回目以降が1回目に温めたページキャッシュを読むだけになるバグがあった。`drop_caches`はスイープ全体の前に1回しか呼んでおらず、この重複に気付かず「chunks=16で秒間2万windows」という物理的にありえない数値を最初に得た。`--seed-offset`で各チャンク数ごとに別々の乱数窓を使うよう修正し、チャンク数ごとに個別に`drop_caches`してから計測し直した**)を追加し、8/16/32/64/100の5点でスイープした。AWS `i4i.2xlarge`(8 vCPU)、1GiB cgroup、8GBデータセット、100ページ窓、200バッチ。

**結果**(修正後):

| チャンク数 | スループット | 対chunks=8 |
|---:|---:|---:|
| 8(コア数) | 498.6 windows/s | 1.00倍 |
| 16 | 686.0 windows/s | 1.38倍 |
| **32** | **717.0 windows/s** | **1.44倍(最良)** |
| 64 | 653.1 windows/s | 1.31倍 |
| 100(1ページ=1SQE) | 572.2 windows/s | 1.15倍 |

### 結論

- コア数(8)は最適なチャンク数ではなかった。32付近まで増やすとさらに1.44倍のスループット向上が得られる。
- ただし「増やすほど良い」わけでもない。100(1ページ1SQE)まで細かく分割すると、SQE1個あたりの作業量に対してSQE発行・完了処理のオーバーヘッドの比率が相対的に増え、頭打ちを超えて悪化に転じる(chunks=8とほぼ同水準まで低下)。
- 32付近のピークが何によって決まっているか(この8 vCPUインスタンスでの`io-wq`ワーカープールのサイズ上限か、NVMeの実効並行度か、他の要因か)は未計測。インスタンスタイプが変われば最適値も変わる可能性が高く、特に本番で使う32 vCPUの`i4i.8xlarge`では別途スイープが必要。

## 結果7: 実装して実システムで検証したところ、Baselineより3〜6倍遅く、差し戻し

結果5・結果6を踏まえ、`scan_impl`にio_uringベースの並列プリフェッチを実際に実装した。`vmemkv::Config`に新しいopt-inタグ`IoUringScanPrefetch`(既存の`BloomFilter`/`T1InlineValue`等と同じタグリストパターン)と、チャンク数を制御する`ScanPrefetchChunkCount`(既定0=自動、`std::thread::hardware_concurrency()`から導出)を追加。`scan_impl`の先頭で、対象キー範囲についてもう一度(安価な)T1走査を行い、非インライン・非トゥームストーンの候補について(generation, offset, size)を集めて隣接範囲をマージし、`madvise(MADV_POPULATE_READ)`をio_uring経由でチャンク分割・一括発行してから、既存の(変更していない)Scan本体を実行する設計にした。CMakeにliburingの検出(`ENABLE_IO_URING`、見つからなければ無害なno-opにフォールバック)を追加し、`test_kv_store`の対象ストア一覧にも加えた。

### 正しさの検証

liburing有効ビルドで、既存の全326テストケースがパス(15万6千アサーション、失敗0)。プリフェッチのロジック自体も単体で確認済み(あるT1T2Reorg状態のScanで、候補100件→マージ後81個の連続範囲、合計約83KB、単発では4.3msで完了)。

### ハング: 原因は並行性

ところが、実際のLTM(1GiB cgroup、8倍オーバーサブスクリプション)環境で**同一Scanを5回連続で呼ぶだけで60秒経ってもタイムアウトする**ことが判明した(1回だけなら成功する)。`ScanPrefetchChunkCount`を1(io_uring発行を完全に直列化)に固定したところ、1363回・1028回の反復でも安定して完走した。**すなわち原因はio_uringの並行発行(既定はコア数=8チャンク)そのもの**であり、極端に逼迫したcgroup環境下では、複数の`io-wq`ワーカーが同時にメモリ確保を試みることが、`mem_cgroup_handle_over_high`(cgroup v2の`memory.high`スロットリング)を直列時より遥かに悪化させていると考えられる(直接の機序は未特定)。

### しかし直列化(chunk=1)でも、Baselineより3〜6倍遅い

同一インスタンス・同一コーパスで、chunk=1のIoUringScanPrefetchとBaselineを直接比較した(いずれも1000回以上の反復で安定した数値):

| | Baseline | IoUringScanPrefetch(chunk=1) | 比率 |
|---|---:|---:|---:|
| Zipf | 2,285.18 items/s | 354.574 items/s | **0.155倍(6.4倍遅い)** |
| Uniform | 812.399 items/s | 244.797 items/s | **0.301倍(3.3倍遅い)** |

並行性のバグを取り除いても、プリフェッチという発想自体がこの実システムでは明確に負けている。

### なぜマイクロベンチマークと結果がここまで乖離したか

結果5・6のプローブ(`prefetch_probe.cpp`)は、1回の作業単位が**連続した100〜256ページ(400KB〜1MB)**という、比較的大きなI/Oコストの塊を相手にしていた。一方、実際のVMemKVのScanは、100件の候補が**分散した81個の小さい範囲、合計約83KB(平均1KB程度)**という、遥かに小さい作業単位だった。「小さすぎる作業単位に対してio_uring発行の固定オーバーヘッドが割に合わない」という仮説を、同じプローブに`--mode scatter-raw`/`--mode scatter-uring`(1つの連続窓ではなく、VMemKVの実測値(81件・平均1056バイト)に合わせた分散した小さいレコード群を生成するモード)を追加して検証したところ:

| 手法 | スループット | 対素タッチ |
|---|---:|---:|
| 素のタッチ(io_uring無し) | 96.0 windows/s | 1.00倍 |
| io_uring chunk=1(直列) | 83.5 windows/s | 0.87倍(13%遅い) |
| io_uring chunk=8(並行) | 94.5 windows/s | 0.98倍(ほぼ同等、**ハングせず**) |

方向性(小さい作業単位ではio_uringが割に合わない)は裏付けられたが、差はわずか13%に留まり、実システムで見た3〜6倍の差も、並行時の数分間のハングも、このプロキシでは全く再現しなかった。つまり**このプロキシに含まれていない、実システム固有の何らかの要因(最有力候補は、T1インデックス自体が8.26M件で約264MB、1GiB予算の4分の1以上を占め、同じ極端に逼迫した予算をT2と奪い合っていること)が、劣化の大部分を占めている**と考えられるが、これは未特定のまま残った。プロキシベンチマークをこれ以上チューニングしても説明できる見込みは薄く、これ以上追うには実際のVMemKVプロセスを直接計測する(ハング中の`memory.stat`/`memory.events`、あるいはperfプロファイル)必要があると判断し、そこまでは実施していない。

### 結論と対応

**このアプローチ(io_uringによるScanプリフェッチ)は、単体のマイクロベンチマークでは有望に見えたが、実システムに統合すると明確な負けであり、不採用と判断した。** 実装(`IoUringScanPrefetch`タグ、`prefetch_scan_range()`、CMakeのliburing検出等)は一式差し戻した(コミット未実施だったため、そのまま`git checkout`で復元)。

この一連の顛末は、本ドキュメント全体に対する重要な教訓でもある。**単純化したマイクロベンチマークで観測された効果は、それが測定している「単位」(ここでは作業サイズ)が実システムの実態と乖離していると、実システムへの統合後にそのまま再現しない**。特に本件のように、実システムには追加の競合するメモリ消費者(ここではT1インデックス)が存在し、極限までメモリが逼迫した環境ではその competing 自体が支配的な要因になりうる。

## 結果8: 結果7「不採用」判断の裏付け — 実装バグではないことの直接的な切り分け

結果7は「3〜6倍遅い理由の大部分が未特定」のまま不採用と結論した。マイクロベンチマークでは圧倒的な性能が出ていたため、「実装に何らかのバグが混入していて、貴重な最適化ネタを見誤って捨てたのではないか」という疑いが残っていた。これを払拭できるまで切り分けることにした。

### まず検討した2つの代替仮説は、いずれも直接測定して棄却した

- **T1インデックスのスワップ仮説**: 「T1(約264MB、1GiB予算の1/4超)自体がLTM圧力下でスワップされ、T2と帯域を奪い合っているのでは」という仮説。本番と同じスワップ構成(NVMe上16GBスワップファイル、`vm.swappiness=100`)を用意した上で `/proc/PID/smaps_rollup` を直接サンプリングしたところ、T1のアノニマスメモリ(`Pss_Anon`)は**一貫して0スワップ**だった。LTM圧力はすべてT2のクリーンファイルページの追い出し・再フォールト(メジャーフォルト53万件以上、スワップ0)として現れており、T1は無関係と確認できた。
- **T1二重走査コスト仮説**: `prefetch_scan_range()`はプリフェッチのために(既存のScan本体とは別に)もう一度T1を走査して候補を集める。この「二重走査」自体のコスト(io_uring抜き、走査・収集・ソートのみ)を最小限のdiagnosticコードで再現して単体計測したところ、Baseline比で**0.996〜1.001倍**、測定誤差の範囲内で無視できるコストだった。

いずれも「未特定の複合要因」の有力候補として挙げていたが、直接測定の結果、どちらも実質的な寄与はないと判明した。

### タイミング計装付きで`IoUringScanPrefetch`を再実装

結果7の実装(コミット前に`git checkout`で差し戻し済み)を、`prefetch_scan_range()`内の各フェーズ(T1走査+収集+マージ、`io_uring_submit()`、CQE待機/回収)に`std::chrono`ベースのタイミング計装を追加した上で再構築した。加えて、`ScanPrefetchChunkCount`を再コンパイルなしで上書きできる環境変数(`VMEMKV_SCAN_PREFETCH_CHUNK_COUNT_OVERRIDE`)を追加し、chunk数を振った比較を高速に行えるようにした。

再実装の過程で、結果7の実装には（今回問題にしていた性能とは別の）**軽微なバグが1つ見つかった**: `VMemKVImpl::name()`が`ConfigT::UseIoUringScanPrefetch`で分岐しておらず、`IoUringScanPrefetch`構成のベンチマーク名が`VMemKV/Baseline`と衝突していた。修正後、`--benchmark_list_tests`で正しく別名(`VMemKV/IoUringScanPrefetch`)として登録されることを確認した。liburing有効ビルドで既存の全テスト(2つの無関係な既存の低速テストケースを除く241件)がパスすることも確認済み。

### chunk=1の遅さは、バッチ化ゼロのsyscallオーバーヘッドで完全に説明できる

i4i.2xlarge(8vCPU)、1GiB LTM cgroup、8.6GBコーパス(8倍オーバーサブスクリプション)、`Scan/T1T2Reorg/Zipf/Value=1KB/threads:1`、chunk=1(結果7で"安定"としていた回避策)で計装ログを採取:

| フェーズ | 平均(30回収束後) |
|---|---:|
| T1走査+収集+マージ | ~14μs |
| `io_uring_submit()` | ~237μs |
| CQE待機/回収 | ~1.41ms |
| **合計** | **~1.67ms** |

同条件でのScan全体の遅延(IoUringScanPrefetch 3.63ms vs Baseline 1.94ms、差分約1.69ms)と、計装で直接測った合計オーバーヘッド(約1.67ms)はほぼ一致した。**chunk=1は候補範囲ごとにsubmit+wait のsyscallペアを逐次実行するため、バッチ化の恩恵がゼロになる**——これは生の`madvise()`より明確に不利な使い方であり、実装のバグではなく、chunk=1という回避策そのものの必然的な帰結だった。

### chunk数を適正化すると、この小規模インスタンスでは3〜6倍もハングも再現しない

同一条件でchunk数を32に戻す(適正なバッチ化を回復させる)と:

| 構成 | IoUringScanPrefetch | Baseline | 比率 |
|---|---:|---:|---:|
| threads:1, chunk=32 | 1.95ms | 1.87ms | 1.04倍(ほぼ同等) |
| threads:4, chunk=32 | 413μs | 404μs | 1.02倍(ほぼ同等) |
| threads:8, chunk=8(自動既定値) | 252μs | 216μs | 1.17倍 |

このi4i.2xlarge(8vCPU)上では、どの構成でもハング・3〜6倍規模の悪化は再現しなかった。なお、threads:1・chunk=32の1回の試行で、プロセスが90秒以上`D`状態(ディスクスリープ)に見え「ハングか」と疑ったが、実際には約3分で完走しており、その時間はほぼコーパスのpopulate/クローンフェーズ(1店舗あたり86〜89秒、2店舗分)と一致していた——Scanフェーズ自体の詰まりではなかった。結果7で報告した「5回連続で呼ぶだけで60秒でタイムアウトする」という観測が、同様にpopulateフェーズの重さとScanフェーズのハングを混同していた可能性は否定できないが、これは当時の実行環境を再現できないため確認できていない(未解決の問題提起として記録するに留める)。

### major fault計測により、「効くはずの条件」を再現できていないことを直接確認

上記だけでは「なぜchunk=32でもBaselineを上回れないのか(マイクロベンチの再現にならないのか)」が説明できない。`bench_kv.cpp`の`execute_benchmark_run()`に`getrusage(RUSAGE_THREAD)`によるメジャー/マイナーフォルト計装(`MajFlt_PerIter`/`MinFlt_PerIter`カウンタ)を追加し、同じLTM条件で直接計測した:

| 構成 | MajFlt/iter (IoUringScanPrefetch) | MajFlt/iter (Baseline) |
|---|---:|---:|
| chunk=1 | 16.23 | 16.27 |
| chunk=32 | 16.23 | 16.27 |

chunk数によらず、IoUringScanPrefetchとBaselineの実測メジャーフォルト数はほぼ完全に一致していた。ここで重要なのは、`RUSAGE_THREAD`は**呼び出しスレッド自身のフォルトしか計測しない**という点である。`MADV_POPULATE_READ`はio_uringの`io-wq`ワーカースレッド(別のカーネルスレッド)上で非同期に実行されるため、プリフェッチ自体が起こすフォルトはこの計測には現れない。つまりこの16.23〜16.27という数字は、**プリフェッチ後に実際に`scan_impl()`がT2レコードを読みに行った際のフォルト数**であり、それがプリフェッチの有無で変わらないという事実は、**プリフェッチしたページが実際に使われる前に、cgroupの継続的な`memory.high`回収圧力によって再度追い出されている**("prefetch-then-evict"競合)ことを強く示唆する。

これは結果5・6のマイクロベンチマーク(`prefetch_probe.cpp`)との乖離も一貫して説明する。マイクロベンチは「プリフェッチした直後に同一ループ内でtouchする」構成であり、他の継続的な回収圧力と競合しない。一方、本ドキュメントのLTM設定は1GiB予算に対し8.6GBコーパス(8倍オーバーサブスクリプション)という極端な条件であり、プリフェッチと実読み取りの間のわずかな時間差の間にすら、ページが再度追い出されるだけの回収圧力が常時かかっている。

### 結論

**実装バグではない。** 2つの独立した測定系列——(a)タイミング計装によるchunk=1オーバーヘッドの内訳一致、(b)major fault計測による"prefetch-then-evict"競合の直接確認——により、「未特定の複合要因」だった結果7の結論は、具体的で理解可能なメカニズムに置き換わった。結果7の不採用判断(madvise常時RANDOM維持、io_uringプリフェッチ不採用)は変わらないが、根拠がはるかに明確になった。

なお、本ドキュメントのLTM設定(8倍オーバーサブスクリプション)は意図的に極端な条件であり、より穏やかな比率(例: 2〜3倍)であればプリフェッチしたページが実読み取りまで生存する可能性があり、結果が変わるかもしれない——ただしこれは本プロジェクトの標準LTM設定とは異なる条件での検証になるため、現時点では優先度を上げていない(「今後の調査候補」参照)。

今回追加した計装コード(`prefetch_scan_range()`のタイミングログ、`VMEMKV_SCAN_PREFETCH_CHUNK_COUNT_OVERRIDE`環境変数、`bench_kv.cpp`の`MajFlt_PerIter`/`MinFlt_PerIter`カウンタ、`IoUringScanPrefetch`タグ一式)は診断専用であり、結果7と同様にコミットせず`git checkout`で差し戻した。`name()`の命名バグ修正は再実装内のみに存在していたバグなので、差し戻しと同時に消える(mainの`vmemkv_impl.hpp`には元々このバグは存在しない——結果7の初回実装で混入し、結果7自体のrevertで一度消え、今回の再実装で再度混入して見つかったもの)。

## 今後の調査候補

**保留した方向性(参考として記録、当面は着手しない)**

- 結果2で考察した「ソート済み境界オフセット」に基づくScan単位のmadvise動的切り替え。技術的には筋が通っているが、advise/revertペアの実装コストと、Get側の実績ある設定に触れるリスクを踏まえて優先度を下げていた。結果7・結果8でio_uring経由の並列プリフェッチ自体が不採用になったため、Scan性能改善の方向性は振り出しに戻っている。
- 結果8で見えた「より穏やかなオーバーサブスクリプション比率(2〜3倍程度)でも同じ"prefetch-then-evict"競合が起きるか」の検証。もし穏やかな比率ではプリフェッチしたページが実読み取りまで生存するなら、io_uringプリフェッチは(本ドキュメントの標準8倍LTM設定ではなく)より軽度なメモリ逼迫下限定の最適化として復活の余地があるかもしれない。ただし本プロジェクトの標準LTM設定とは異なる条件での検証になるため、現時点では優先度を上げていない。
- 結果8で未解決のまま残った問題提起: 結果7の「5回連続Scanで60秒タイムアウト」という観測が、実際にはpopulateフェーズの重さ(結果8で確認した86〜89秒規模)を誤ってScanフェーズのハングと解釈していた可能性。当時の実行環境が再現できないため未確認。

**解決済み(参考: 結果8)**

- ~~結果7で未特定のまま残った「実システム固有の劣化要因」(T1インデックスの competing memory pressure 説)~~ — 結果8でT1のスワップ・T1二重走査コストいずれも直接測定の上棄却済み。実際の劣化要因は、極端なオーバーサブスクリプション下での"prefetch-then-evict"競合(major fault計測で確認)とchunk=1のバッチ化ゼロオーバーヘッド(タイミング計装で確認)の2つで説明がついた。
