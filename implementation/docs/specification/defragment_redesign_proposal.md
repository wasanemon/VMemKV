# T2 Defragment 再設計提案：逐次書き換え方式

**ステータス**: 実装済み(`defragment_internal()`、単一スレッド版。low_level_design.md 4.6 節が同じ機構を記述する)

## 1. ゴール

1. **設計制約**: 新規状態を追加しない。RocksDB 等の LSM-tree 型コンパクション(レベル、複数ソート済みランのマージ)を持たない。
2. **スケーラビリティ**: 1バイトあたりのコストが corpus_size に対して劣化しない(シーケンシャル I/O のみ)。
3. **Insert スループット**: defragment() のスループットが Insert のピークレートを上回る(Scan 性能含む)。
4. **並行TPS**: defragment() 実行中の並行書き込みスループット低下を最小化する。

## 2. 前提

defragment() の各サイクルの出力(新しい base 領域)は常にキー順で構築される。したがって**前回サイクルの base は既にキー順にソート済み**であり、「base を物理オフセット順に読む」ことと「base をキー順に読む」ことは同一操作になる。

T2 の生きているマッピング(`T2Memory::base`)は **MAP_PRIVATE** である。in-place の書き込みはこのプロセスのメモリ上にしか存在せず、`checkpoint_internal()`/`defragment_internal()` が明示的に `pwrite()` するまでディスク上には現れない。両者とも、その時点で**生きているものだけ**を `pwrite()` する。したがって、一度も再durabilize されないまま死んだレコードは、そのスロットに一度もバイトが書かれたことがない(ゼロ埋めでもホールパンチでもなく、単に未書き込み)。base 領域は密に詰まった連続レコード列ではなく、**生バイトをヘッダーとして順次パースする走査は成立しない**。

## 3. 機構

### 3.1 生存オフセット+サイズヒント収集(T2 I/O ゼロ)

`t1_.scan()` を一度呼び、生存(tombstone でも inline でもない)エントリの `payload_bits` そのもの(オフセットだけでなく、上位ビットに埋め込まれた block_count サイズヒントも含む)を `base_boundary` 未満のものだけ集め、オフセット昇順にソートする(`live_payloads`)。純粋にインメモリの操作。

### 3.2 base 領域の読み取り

`live_payloads` の各エントリを昇順に、既存の `try_read_base_record()`(get_impl() の大レコード読み取りと共有、`BaseReader::kScan` モード)経由で読む。このヘルパーは block_count サイズヒントを使って読み取り範囲を決め、小レコードは madvise 済みの走査用マッピング、大レコードは常駐判定 (`mincore()`) 後に必要なら `pread()` にフォールバックする。まれに `nullopt` を返すケース(`mincore()`/`pread()` 失敗など)は `t2_.at()` の無同期読み取りにフォールバックする(seqlock 不要: `old_base_boundary` 未満のオフセットは、後述の watermark 凍結によりこのフェーズ全体で不変であることが保証済み)。

**2節の理由により、T1 が今この瞬間に保証するオフセット以外には一切触れない** —— 生バイトを順次パースする設計ではない。読み取ったレコードは、scratch ファイルへ(まだ最終出力ではない、3.3節参照)昇順のまま(=キー順のまま)追記する。

### 3.3 tail のマージ

writer 停止後(`stop_writers_and_wait()` の後)、`tail_entries_.drain_and_clear()` で直近の書き込みを完全な形で取得し、キー順にソートする。この時点で新規の書き込みは発生し得ないため、watermark のインクリメンタルな前進は不要(checkpoint_internal() と異なり、tail 処理を writer 稼働中に行わないため)。

scratch ファイル(キー順)と、ソート済み tail 候補(キー順)を、マージソートの併合ステップと同様にキー順でマージし、実際の出力ファイルへ書き込む。キーが衝突した場合は tail 側が勝つ(scratch 側は必ず古い、既に上書きされたコピーである)。base 領域が常にキー順ソート済みという前提(2節)は、tail 由来のレコードが**必ずこのマージを経てから** base に組み込まれることで維持される。

### 3.4 サイクルトリガー

本設計の1サイクル(3.1 → 3.2 → 3.3 → 新世代の `swap_memory()` による公開)全体を発火させるトリガー。T1 の Soft/Hard しきい値パターン(low_level_design.md 4.5)と同様、tail の蓄積量に基づく自動トリガーとする。corpus_size や WAL バイト数には依存しない。checkpoint_internal() 側の swap(同一ファイル内で base_boundary を前進させるだけで再配置は行わない、物理回収不可)とは別のイベントである。

### 3.5 並列化(未実装)

3.2 の読み取り+書き込みは単一スレッドで実行する。ワーカースレッドに分割する余地はある(`live_payloads` は既にソート済みなので、チャンク境界を等分に選べる)。64KB LTM は単一スレッドでは Insert の実効レートを下回る(6節)。

## 4. バックプレッシャー

defragment() の swap サイクルが直近の書き込みレートに対して十分な速度で完了していないことを検知した場合、書き込み側を一時的に減速させる。大レコード(64KB 級)のコンボでは、defragment() のスループットが Insert のピークとほぼ互角にしかならないケースがあり、この機構で被害を抑える。検知条件・減速量は未設計。

## 5. 正しさ・安全性

- レコードは常に新しいオフセットへ再配置してから再公開する(relocate-and-republish)。生存中の base バイトを in-place で書き換えることはない。
- T1 の反映は `t1_.reorganize()`(全 T1 の O(corpus) 再構築、offset_mapper 経由で `payload_bits` を書き換え)を使う。checkpoint_internal() と共通の、既に実証済みの単一原子的公開点。
- `capture_watermark_` は `old_base_boundary` に一度だけ凍結する(サイクル中インクリメンタルに前進させない)。base 領域全体をサイクル開始と同時に一括保護できるため十分であり、tail の catch-up(3.3節)を writer 停止後にのみ行うことで、checkpoint_internal() が必要とするインクリメンタルな前進(offset 順の逐次クレーム)を回避している —— この単純化は「tail 処理中に writer が存在しない」という設計上の選択に依存する。
- 新しい世代の公開は既存の `swap_memory()`/`ThreadReferenceTracker::wait_until_retired()` を使う。新規プリミティブは不要(T1Index に新しいインタフェースを追加していない)。
- 新規ファイル + `rename()`。旧ファイルは最後の読者が世代を手放すまで実データを保持する(unlink-while-open)。

## 6. ゲート評価

| ゲート | 判定 |
|---|---|
| 1. 設計制約 | PASS |
| 2. スケーラビリティ | PASS。churn=0 のコーパスサイズスイープが4コンボ×4段階(25/50/75/100%)全16点で完走する(8節) |
| 3. Insert スループット | 1KB系 PASS(負荷率 r=0.14〜0.32、余裕あり)。**64KB系 FAIL(単一スレッドで r=1.69、依然 Insert に劣勢)** —— 3.5節の並列化が必要 |
| 3. Scan局所性 | 有界・非蓄積(swap ごとにリセット)。tail 分の一時的な非相関は残る |
| 4. 並行TPS | **FAIL**。同時書き込み時、defragment() 自体が60秒の内部タイムアウトに到達(単独実行なら余裕を持って完走する同じコーパスで)。書き込み側TPSも ltm/1KB で-79%、ltm/64KB で-98% と大幅に低下(8節) |

## 7. 未解決事項

- swap 頻度のデフォルト値
- **並列化(3.5節)**: 未実装。64KB LTM で Insert に対する優位性が不足(ゲート3 FAIL)
- **並行TPSの悪化(ゲート4 FAIL)** への対策 —— バックプレッシャー(4節)、または defragment() 自体の並列化で緩和できるか要検証
- バックプレッシャーの検知条件・減速量
- 偏った書き込みパターン(Zipf 等)での挙動

## 8. 実測値

AWS i4i.8xlarge、LTM は cgroup メモリ制約下。`defragment_internal()`(本実装、単一スレッド版)、2026-08-23 実測。

### コーパスサイズスイープ(churn=0、単独実行、フルコーパス=ratio 100%)

| combo | 所要時間 | スループット | Insert 実効レート(参考、同一実行内の isolated write TPS) | 負荷率 r |
|---|---|---|---|---|
| in_memory/8B | 3.10 s | 6,452,141 rec/s | 119,679 rec/s | 0.019 |
| in_memory/1KB | 21.9 s | 365,022 rec/s | 49,601 rec/s | 0.136 |
| ltm/1KB | 53.4 s | 154,566 rec/s | 49,340 rec/s | 0.319 |
| ltm/64KB | 27.4 s | 4,784 rec/s | 8,097 rec/s | **1.69(発散)** |

25/50/75% の中間段階も含め全16点が完走する(8節)。64KB のみ、単一スレッドでは Insert に追いつかない。

### Concurrent-Write Contention spot check(32 writer threads、ratio=100%)

| combo | isolated write TPS | concurrent write TPS | 低下率 | defragment() 所要時間 |
|---|---|---|---|---|
| in_memory/8B | 119,679/s | 107,735/s | -10% | 4.13 s |
| in_memory/1KB | 49,601/s | 17,683/s | -64% | 35.99 s |
| ltm/1KB | 49,340/s | 10,557/s | -79% | ≥60 s(タイムアウト) |
| ltm/64KB | 8,097/s | 168/s | **-98%** | ≥60 s(タイムアウト) |

単独実行では余裕を持って完走する同じフルコーパス(ltm/1KB 53.4s、ltm/64KB 27.4s)が、並行書き込み下では60秒以内に完了しない。書き込み側のTPSも大きく低下する。
