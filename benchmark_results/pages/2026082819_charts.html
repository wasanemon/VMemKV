今回の主目的は、checkpoint()の自動発火が大きな値サイズ(64KB)のInsert主体ワークロードで実質的に一度も発火しないバグの修正(commit 6aec324)。maybe_reorganize_if_needed()がWALバイト閾値(WalMaxBytesSinceCheckpoint、既定64MiB)を一度も評価しておらず、エントリ数ベースの閾値(T1 append領域・tail_entries_)だけに依存していた -- 64KB値では前者がT2の実データ量換算で約137GB・約34GBに相当し、64MiB閾値を事実上無力化していた。AWS実スケール(i4i.8xlarge, 32書き込みスレッド, LTM cgroup, 64KB値, 180秒)で修正後にbacklogが有界化し、時間経過とともにcorpus比で縮小することを確認(4.0%→0.015%)。合わせて、checkpointの各フェーズ(msync/T1 reorganize/writer停止/barrier drain/WAL rotate、WAL rotateのgroup-commitリーダー待ち内訳)と、writerが実際にブロックされた累積時間をVMemKVStatistics経由で常時観測できるようにした(commit db31a6b)。この計測により、checkpoint所要時間を実際に支配しているのはmsyncでもT1 reorganizeでもなく、WALのgroup-commitリーダー選出待ちであること(データ量ではなく書き込み並行度に依存)を発見。時間ベースのcheckpoint間隔オプション(CheckpointIntervalMs)も追加し、0.2秒〜60秒の間隔で比較したが、今回検証した範囲ではQPSへの有意な悪影響は見られなかった。

本ラウンドは--without-rivalsで計測(VMemKV内部のみの変更のためRocksDB/RocksDB-BlobDB/LMDBは前回2026082101の数値をそのまま再利用・マージ)。主要CRUD/YCSB-Eマトリクス(4コンボ×99ベンチマーク)は全て正常完了。一方、既存の補助probe(run_maintenance_contention_probe.shのcheckpoint_contention/reorg_contention、および一部のdefrag/checkpoint-throughputスイープ)で、LTMのフルコーパス・高並行度地点が300秒の外側タイムアウトに達し測定不能になる退行を発見。gdbでの直接観察とAWS上でのA/B比較(本ラウンドの3コミット適用前bc9bfd2 vs 適用後a3bb115で完全に同一の挙動)により、これは今回のcheckpoint修正が原因ではなく、2026-08-21のレポート以降に混入した既存の退行(WALのgroup-commitリーダー待ちが極端に長くなる)であることを確認 -- 詳細はTODO.md項目6を参照。主要マトリクスは無影響。

Stacking Variants

各最適化の詳細は Design Document を参照。

  • RocksDB: LSM-Tree のベースライン比較
  • LMDB: B+Tree / mmap ベースの比較対象
  • RocksDB-BlobDB: RocksDB の Blob 分離ストレージ変種(大きな Value 向け)
  • Baseline: vmemkv 最適化なし
  • +BF: + T1 Bloom Filter
  • +Inline: +BF + T1 Inline Value(<8B のValueをT1のみで処理)
  • +Prefault: +Inline + T2 Async Prefaulting(全部盛り、= VMemKVStore)。旧ScanBaseSequentialアブレーションは実測の結果撤去され、その最適化(base領域専用mmap経路)はGet/Scan双方の標準パスへ無条件で統合済み。

Environment

  • Instance: AWS i4i.8xlarge (ap-northeast-1) x4 (4並列独立インスタンス、run_4parallel_bench.sh --without-rivals フルラン) + A/B検証用単体インスタンス x1(TODO.md項目6の退行切り分け)
  • CPU: Intel Xeon Platinum 8375C @ 2.90GHz (32 cores)
  • RAM: 247.7 GiB
  • RAM (Larger-Than-Memory): cgroup で DRAM を制限し、target_ratio 相当のコーパスを構築後、cgroup内で計測(ストアごとに独立したcgroupスコープ + drop_caches)
  • Disk: Local NVMe SSD, ext4
  • Kernel: 6.17.0-1019-aws
  • Git Rev: a3bb115(本ラウンドのVMemKV計測)、RocksDB/LMDB/RocksDB-BlobDBの数値は2026082101(4a7084c)から再利用

Workloads

  • Insert: 順次挿入(1/4/16/32 スレッド)
  • Get Hit/Miss (Zipf/Uniform): ポイントルックアップ
  • Update / Delete: Zipf 分布での更新・削除
  • Scan (Zipf/Uniform): レンジスキャン(旧レポートにあった reorganize モード分割は撤去済み)
  • YCSB-E: 95% Scan + 5% Insert 混合(32スレッド / 30秒タイムライン)

Insert Workload

実験概要: ユニークキーを空のストアに順次挿入する際の書き込みスループット。

Update (Zipf) Workload

実験概要: Zipf 分布での既存キーに対する更新スループット(ステートフルな上書き)。

Delete (Zipf) Workload

実験概要: T1 Tombstone 付与による並行削除スループット。

Get Miss (Zipf) Workload

実験概要: 存在しないキーへの読み取り。Bloom Filter の偽陽性回避効果を評価。

Get Hit (Zipf) Workload

実験概要: Zipf 分布(ホットキー偏重)での既存キーに対するポイントルックアップ。get_impl() の base_mmap 高速パス(本ラウンドの主要変更)が最も効くケース。

Get Hit (Uniform) Workload

実験概要: 一様分布での既存キーに対するポイントルックアップ。同上。

Scan (Zipf) Workload

実験概要: Zipf 分布で選ばれたレンジのスキャン。現行 bench_kv は reorganize 状態を単一の Scan ベンチマークとして測定する形に統合済み(旧レポートの Scan_WithReorg / Scan_T1T2Reorg モード分割は撤去済み)。

Scan (Uniform) Workload

実験概要: 一様分布で選ばれたレンジのスキャン(同上)。

YCSB-E — Scan + Insert 混合スループット(30秒タイムライン)

YCSB-E ワークロード: 95% Scan(100件レンジスキャン)+ 5% Insert を 32スレッドで 30秒間実行。 藍色の点線: 自然発生のT1 Reorganize(Adaptive Soft Limitによる自動トリガー、全バリアント共通)。 強制トリガーはバリアントごとに独立集計(全バリアント共通の1本の線には集約しない): t=5秒予定のreorganize()(細かい点線)、t=10秒・t=25秒予定のcheckpoint()(粗い点線)を、そのバリアント自身の色+マーカー形状(スキャンQPS線をホバーした際の点と同じ形。凡例のポイント形状も対応)で描画。 実際に発火する秒(線の位置)は予定秒とは限らない(将棋倒しに対するガード無し、書き込み負荷次第で数十秒遅延することがある)。8B In-Memoryのように挿入スループットが極端に高いワークロードでは、t=5秒予定のreorganize()自体が20秒以上かかり、後続のcheckpoint()トリガー(t=10s/25s)がこの30秒間に一度も発火しないまま終わることもある(この場合、線は1本しか出ない)。カーソルを線に合わせると、その秒に発火したバリアント・種類・予定秒・実発火秒・所要時間を表示。
